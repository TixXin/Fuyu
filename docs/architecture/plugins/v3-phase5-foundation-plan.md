## 一、要你定的问题

前四条是方案里写明「实现时再定」的；后面几条是读下来发现方案没写、但开工就要用到的。每条给推荐、理由、备选和代价。

### Q1 逐版审核：哪些更新能快速通过、谁来批（决定 8）

**推荐：每个版本都要人点「批准」，CI 把版本分成三档，绿档扫一眼就批。**

| 档 | 条件 | 怎么处理 |
|---|---|---|
| 绿 | 和上一个审过的版本比：没有新的 `nodeApis`、没有新的联网域名、没有新增或升级的 npm 依赖、没有命中敏感模式（下面的「黄」）、源码改动不超过约 300 行 | 维护者看 CI 贴的摘要和差异，点批准 |
| 黄 | 新的 `nodeApis`（尤其 `child_process`、`net`、`fs` 写到插件目录外）、新的联网域名、依赖变化（锁文件里新增或升级的包逐个列出）、动态 `import()` 非字面量、`vm` / `Function` / `eval`、读写别的插件或浮屿的数据目录、`provides` / `replaces` 变化、长字符串或 base64 大块 | 维护者逐项看，必要时要作者说明 |
| 红（自动拒绝） | 带可执行程序或 `.node`、代码混淆、用了 `experimental` 接口、名字违规、`engines.fuyu` 缺失、构建失败、作者签名不对或密钥变了 | CI 直接失败，不进人工 |

- 分析器同时给作者用（`fuyu-plugin review <旧提交> <新提交>`），作者提交前就能看到自己落在哪档。
- 批准人：现在只有你（TixXin）。可以让本机的 Claude 会话先读差异、写一份审核意见贴在 PR 上，你看完点批准；**AI 的意见只是草稿，不能代替人批**。CI 里不跑大模型（要往跑第三方代码的任务里放 API 密钥）。
- 备选 A：绿档不经人、自动上架。省事，但违背「每个版本都审」，而且投毒者会刻意把改动做成绿档（例如藏进已有依赖的升级里，所以依赖变化一律算黄）。
- 备选 B：不分档，全部细看。插件少时可以，但两三个插件就会把审核变成每周的固定负担。
- 插件多到审不过来时（方案里写的）再改成只对热门的和黄档做人工审核，到时再问你。

### Q2 冷静期：天数和几个细节（决定 9）

**推荐：维持 3 天**，并定下这几个细节：

- 从**市场上架的时间**（索引里的 `publishedAt`，CI 写）算，不从作者打标签的时间算。
- 只管**自动更新**。手动点「更新」可以立刻装，确认框里写「这个版本上架不到 3 天」。
- **新安装也默认装过了冷静期的最新版**；插件只有冷静期内的版本时（刚上架）照装，标「刚上架」。不这样的话冷静期对新用户没用。
- 「安全修复立即推送」只有维护者能在 PR 里标（`urgent`，必须写原因），岛上的更新说明里显示这个原因。
- 备选：7 天。被发现的投毒多数在几小时到几天内曝光，7 天更稳；代价是正常的修复 bug 版本要等一周才自动到用户手上。

### Q3 不走市场的手动安装：默认开还是关（决定 14）

**推荐：默认关**，设置的插件页里打开一次（打开时再弹一次说明）。

- 关着的时候双击 `.fuyu`：浮屿照样打开，但只说明「手动安装没有打开」和怎么打开，不安装。
- 理由：手动安装是整套保护里最弱的一环（审核、冷静期、市场构建都管不到），而「把这个文件双击一下」正是最容易的社会工程。Obsidian 对社区插件就是默认关、开一次。
- 备选：默认开，只靠醒目的「未经审核」确认框。分享内部工具方便一步，代价是确认框会被习惯性点掉。
- 开发模式（从文件夹加载）是另一个开关，不受它影响。

### Q4 开源基座的名字和许可证（决定 15）

**推荐：许可证现在就定 MIT**（`packages/plugin-base` 已经写的是 MIT，和 Cordis、rutis、Tauri 一致）；**名字照方案到公开前再定**。

- 第 5 阶段新加的几个包（清单、市场、构建工具）现在都用 `@fuyu/plugin-*` 这样的私有名字开发，代码里浮屿专有的名字（清单里的 `fuyu` 键、`.fuyu` 后缀、`~/.fuyu`）都做成可配置的，公开时只改包名。
- 想先有个候选的话：避开 `tauri-plugin-*`（那是 Tauri 自己 Rust 插件的命名空间，会混淆）。沿着「岛」的意思可以是 Archipelago、Atoll、Lagoon 这类；不急。

### Q5 作者签名：必须签吗、签什么

方案说「作者签的是提交号」，第 2 版的作者签名是可选的。

**推荐：上架市场的插件必须签**，签的是一段带分隔的文本 `fuyu-plugin-commit/1 \n <插件名> \n <版本> \n <仓库> \n <提交号>`，Ed25519，沿用第 2 版的密钥格式（作者已有的密钥可以继续用）。`fuyu-plugin publish` 一条命令打标签、签名、开市场 PR，作者不用手动处理。

- 理由：第 3 版每个版本本来就要作者交提交号，多签一下几乎不增加负担；只有必须签，「作者换密钥 = 重新上架」那条规则才有意义，也才挡得住「作者 GitHub 账号被盗、攻击者交了一个新提交号」。
- 备选：可选签名（第 2 版的做法）。门槛低一点；代价是没签的插件没有这层保护，规则也要多一套分支。
- 现在的第三方作者只有 ShengLin1001（两个插件），第 6 阶段迁移时一起帮他生成密钥。

### Q6 官方插件怎么签（签名私钥只在 Windows 的现实）

倒数日、闹钟、世界时钟（E37）、文件搜索（C67）这些官方插件第 3 版要上架；第 2 版的官方作者密钥在 Windows 那台机器上、用 DPAPI 绑在一个账户里。

**推荐：官方插件也走市场构建，作者证明换成「这个提交在 `TixXin/fuyu` 受保护的 `main` 上」**，不用私钥。

- `TixXin/fuyu` 的 `main` 只能经 PR 合入、要过 CI，市场 CI 用 GitHub 的接口确认提交号在 `main` 的历史里，就等于「官方作者认可了这份源码」。官方插件照样过审核分析器、照样有冷静期。
- 好处：Mac 和 Windows 上都能发官方插件，不用每次去 Windows；也不用把官方密钥复制到第二台机器。
- 代价：官方插件的信任落在 GitHub 账号和仓库规则集上（能往 `main` 合 PR 的人都能发官方插件版本，现在是你和 ShengLin1001）。要更严可以只认 `plugins` 目录由你批准的 PR（CODEOWNERS）。
- 备选 A：沿用 Windows 上的官方作者密钥，每发一次官方插件都要到 Windows 上签。
- 备选 B：新生成一把第 3 版的官方作者密钥，Mac 和 Windows 各放一份。两台机器都是泄露点。

### Q7 市场仓库 `TixXin/fuyu-plugins` 的 `main` 怎么保护

逐版审核要求「上架 = 经 PR 合入并被批准」，但它的 `main` 现在没有规则集：索引、点赞、主题三个工作流直接推 `main`，GitHub 不允许个人仓库把 Actions 设成规则集的绕过者（[market-ops.md](market-ops.md)）。方案写了第 5 阶段前要解决。

**推荐：给这三个工作流一把有写权限的部署密钥**（私钥放在只有 `main` 能用的环境 secret 里），然后加规则集：`main` 必须经 PR、要一个批准、要过检查，只让部署密钥和管理员（只能在 PR 上）绕过。

- 第 3 版的索引还是放在这个仓库（`index.v3.json`，方案已定），旧索引冻结给旧版岛屿。
- 备选 A：把仓库移到一个 GitHub 组织下，就能直接让 Actions 绕过。改仓库地址，旧版岛屿读的是写死的地址（会跳转，但要实测），风险比部署密钥大。
- 备选 B：不加规则集。那「每个版本都审」只是约定，有写权限的人或被盗的令牌能直接推。
- 这一步要你在 GitHub 设置里点（生成部署密钥、建环境、建规则集），我写好步骤。

### Q8 市场索引的过期时间

方案定了索引加「版本号和过期时间」：浮屿拒绝比见过的更旧的索引，过期后提示「市场信息过期」。

**推荐：7 天过期，CI 每天重签一次**（内容没变也换新的过期时间）。过期时：已装的插件照常运行，暂停自动更新和新安装，市场页提示「市场信息过期」。

- 理由：过期时间防的是「有人一直给你一份旧的、签名有效的索引」，好把撤销藏起来；7 天把这个窗口卡在一周内。GitHub 的定时任务不准点（实测平均 6.7 小时一次、最长近 11 小时），公开仓库 60 天没有提交还会被停掉定时任务，所以不能设得太短。
- 备选：3 天（更紧，但 CI 坏一两天用户就会看到过期提示）；30 天（几乎不会误报，但撤销能被藏一个月）。

### Q9 撤销：分几级、谁来签

方案写了「停用而不是删除；分级（提示、停用）；撤销用的签名密钥离线保管」。

**推荐两级**：`warn`（插件页和岛上提示原因，有修复版时优先推）和 `disable`（停掉这个版本、不能再启用，数据保留，用户可以卸载或换到没被撤销的版本）。不做第 2 版的 `uninstall`（删除插件目录）。

**签名推荐用一把单独的撤销密钥**，由你在自己的电脑上用 `pnpm market:revoke` 签好再开 PR；CI 的索引密钥不能签撤销名单。

- 理由：浮屿对撤销名单只增不删（第 2 版就是这样），所以误撤销很难收回；把撤销和日常的 CI 密钥分开，CI 密钥泄露时攻击者没法大面积停用插件。撤销名单的「收回一条」也用这把密钥签。
- 这把密钥可以在 Mac 上生成（不必在 Windows），加密存放并另做离线备份。
- 代价：紧急撤销要你本人在电脑前。备选：CI 密钥也能签撤销名单，响应快，但上面说的风险就在了。

### Q10 第三方插件的名字

方案的示例名字是 `@someone/fuyu-weather`，但市场规则又写「含 `fuyu` 的名字留给官方」，两处矛盾。

**推荐：第三方插件必须用 `@<GitHub 用户名或组织名>/<名字>`，作用域就是源码仓库的所有者**（CI 核对）；`@fuyu/*` 留给官方；作用域内的名字可以带 `fuyu`（`@someone/fuyu-weather` 合法），不带作用域的名字不收。

- 理由：作用域和仓库所有者绑在一起，就不会有人抢注别人的名字或冒充；第 2 版的 `io.github.<用户>.<名字>` 也是这个思路。
- 备选：允许任意名字，靠「去掉标点后不能重名」防冒充。灵活，但要维护者判断「像不像冒充」。
