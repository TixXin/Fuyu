# 插件的独立窗口（设计稿）

> 状态：**用户已定方向**（2026-11-13，决定见第 11 节）。任务 [E31](/docs/tasks/E/E31.md)，issue 201；后续任务 E32（原型）、E33（岛上的简版启动台）、E34（窗口接口）。外部产品的做法见 [docs/research/plugin-windows.md](/docs/research/plugin-windows.md)。原型已做（2026-11-14，E32）：通过，有三处按实测修正，见第 9 节。
>
> 第 1、2 期已实现（2026-11-14，E34），在实验通道里；和本稿不一样的地方见第 12 节。

## 0. 摘要

现在插件的界面都在岛屿自己的窗口里。要做启动台、桌面小组件这类插件，需要岛屿之外的窗口。

定下来的做法：

- **窗口由插件自己建、自己管。** 插件在运行时调用接口新建窗口，决定它的位置、大小、层级、透明度，什么时候显示、隐藏和关闭。清单里不用预先列出窗口。
- **窗口本身仍由岛屿的原生层创建。** 插件发请求，岛屿照做。这样 PowerShell 和 Node 插件也能用，页面也能继续被隔离。
- **页面沿用现有 `webview` 模板的隔离**：岛屿自己创建的 WebView2，所有请求和跳转在原生层拦截，页面只能和自己的插件进程通信，不能联网。
- **分两种窗口**：浮层（能拿键盘焦点，适合启动台）和小组件（不拿键盘焦点，适合桌面组件）。
- **先进实验通道，先只做 Windows**，分四期，合计约 5 周。

## 1. 窗口由谁建、谁管

| 做法 | 说明 | 结论 |
|---|---|---|
| 插件进程直接调系统接口建窗口 | `.exe` 插件今天就能这样做，岛屿不参与 | 不算支持：PowerShell 和 Node 插件做不了，窗口不跟随主题，页面没有隔离 |
| 岛屿用 Tauri 窗口建 | 和设置窗口一样 | 不行。Tauri 建的页面都带命令通道，本应用没有应用级权限清单，本地来源的页面能调用全部命令（[p8-webview-validation.md](/docs/investigations/p8-webview-validation.md) 第 2 节） |
| 岛屿建并管理，插件只在清单里声明 | 本稿第一版的推荐 | 用户 2026-11-13 否决：插件要能自己建窗口和管理 |
| **插件通过接口建和管理，岛屿的原生层执行** | 一个不经过 Tauri 的 Win32 顶层窗口，里面是现有的 `win32::webview_page`；建几个、放哪里、什么时候开关都由插件说了算 | **采用** |

和 uTools 的 `createBrowserWindow` 相比，插件得到的控制权差不多，区别在于页面：uTools 的窗口页面能用 Node.js 的全部能力，这里的页面什么宿主能力都没有，要做事得找自己的插件进程。

岛屿保留的只有几条护栏（第 5 节）和用户的总开关，不替插件决定窗口的样子。

## 2. 隔离是否还成立

现有页面的隔离全部挂在 WebView2 控制器上，和它的父窗口是谁无关（[webview_page.rs](/src-tauri/src/win32/webview_page.rs)）：

- `WebResourceRequested` 过滤 `*`，只回答页面来源下、入口文件夹里的文件，其余返回 403。
- `NavigationStarting` 和 `FrameNavigationStarting` 取消一切离开页面来源的跳转。
- 新窗口、权限请求、下载全部拒绝；关掉宿主对象、脚本对话框；InPrivate，不落盘。
- Tauri 的命令通道是按 webview 注册的，这个控制器上没有。

`webview_page::create` 本来就只要一个 WebView2 环境和一个父窗口句柄。把父窗口从岛屿窗口换成新建的原生窗口，这些都不变。所以判断是：**隔离成立，但要用原型重新验证一遍**，因为下面几处是新的。

| 新情况 | 现在 | 要做的 |
|---|---|---|
| 键盘焦点 | 页面在岛屿窗口里，焦点由岛屿管 | 浮层要拿焦点才能打字。`AcceleratorKeyPressed` 里处理 Esc，别的浏览器快捷键继续禁用 |
| 透明和圆角 | 页面背景透明，底下是岛屿 | 顶层窗口要自己透明。WebView2 在分层窗口上的透明有限制，原型里试两条路：DWM 圆角加不透明底色；或合成宿主（`CreateCoreWebView2CompositionController`） |
| 拖动 | 不需要 | 页面里的 CSS 拖动区需要较新的 WebView2；保守做法是页面发消息、插件调 `window.update` 移动，或岛屿提供「开始拖动」的页面接口 |
| 环境 | 从岛屿的 webview 拿 | 不变。岛屿窗口一直在（只会隐藏） |
| 同一插件多个页面共用来源 | 已是如此 | 原型确认：同一插件的窗口页面和岛上页面**共用存储**，也能用 `BroadcastChannel` 互相通信；不同插件之间读不到（第 9 节） |
| 页面数量 | 每个插件最多 2 个，只在可见时存在 | 窗口可以常驻，每个约 25 MB。要有上限，见第 4 节 |

原型要重跑 p8 第二轮的全部检查（调用不了岛屿命令、任何请求到不了网络），再加上表里的五项。

## 3. 两种窗口

`kind` 在新建时指定，之后不能改。两种的差别只在焦点上，其余属性插件都可以设。

| | 浮层 `panel` | 小组件 `widget` |
|---|---|---|
| 用途 | 启动台、快速输入、选择器 | 时钟、天气、监控、便签 |
| 键盘焦点 | 能拿 | **不拿**，只收鼠标。`WS_EX_NOACTIVATE` 不够，原生层要在窗口被激活时把焦点还回去（第 9 节） |
| 什么时候能显示 | 用户刚操作过这个插件（第 5 节） | 随时 |
| 默认层级 | 置顶 | 贴在桌面上 |
| 岛屿画的标题条 | 有 | 没有 |
| 任务栏、Alt+Tab | 不出现 | 不出现 |

小组件不拿键盘焦点是特意的，用户已同意：它可以一直在屏幕上、随时出现，如果还能收键盘输入，就能做成一个仿冒的密码框。要输入的东西去浮层或岛上的表单页。

**插件能设的属性**：位置和大小（屏幕坐标，可以指定哪块屏幕）、最小和最大尺寸、能否由用户拉伸、层级（贴桌面 / 普通 / 置顶）、透明度、是否点击穿透、标题、失焦时是否自动隐藏（浮层）。

**用户留着的**：设置 → 插件扩展 → 窗口里，按插件有「不允许置顶」「不允许点击穿透」「隐藏这个插件的全部窗口」三个开关；小组件上按住修饰键可以拖走，位置变化会通知插件。记住位置是插件自己的事（用 `storage`）。

## 4. 清单和协议

以下都放在实验通道里，名字在转正前可以改。

**清单**只要权限，不用列窗口：

```json
"experimentalApis": ["windows"],
"permissions": ["windows"]
```

**方法**（插件调用岛屿）

| 名字 | 说明 |
|---|---|
| `window.create { id, kind, entry, bounds?, screen?, layer?, opacity?, title?, resizable?, minSize?, maxSize?, clickThrough?, hideOnBlur?, visible? }` | 新建。`id` 由插件起，同一插件内唯一；`entry` 是插件文件夹里的一个 HTML。返回实际的位置和大小 |
| `window.update { id, … }` | 改上面除 `kind`、`entry` 以外的任何属性 |
| `window.show { id }` / `window.hide { id }` | 显示、隐藏。隐藏不销毁页面 |
| `window.focus { id }` | 只对浮层 |
| `window.close { id }` | 关闭并销毁页面 |
| `window.list` | 这个插件现有的窗口和它们的状态 |
| `window.postMessage { id, message }` | 发给页面，上限 256 KB |
| `screens.list` | 每块屏幕的工作区、缩放和是否主屏，用来算位置 |

**通知**（岛屿发给插件）

| 名字 | 什么时候 |
|---|---|
| `window.message { id, message }` | 页面发来消息 |
| `window.bounds { id, bounds, screen }` | 用户拖动或拉伸了窗口，或屏幕变化后窗口被挪回屏幕内 |
| `window.focused { id, focused }` | 浮层得到或失去焦点 |
| `window.closed { id, reason }` | 窗口没了：用户关掉、用户在设置里隐藏、屏幕拔掉、超出上限 |
| `screens.changed` | 屏幕增减或分辨率变了 |

- 页面里的接口沿用 `acquireFuyuApi()`，多三个方法：`close()`、`startDrag()`（用户按住时开始拖动窗口）、`resize(width, height)`。主题变量同现在的无边框网页页面。
- **上限**：每个插件同时 8 个窗口，整个岛屿 24 个；尺寸 48 像素到所在屏幕的工作区；窗口至少有 48 像素留在某块屏幕内，否则岛屿把它挪回来并发 `window.bounds`。`window.update` 每个窗口每秒最多 30 次，多的合并。
- **生命周期**：窗口属于插件进程。进程退出、插件被停用或岛屿退出时，它的窗口全部关闭；进程崩溃后重启，要自己重新建。有窗口开着的插件不会因为空闲被停掉。
- 能力 `windows`，实验期间放进 `initialize.experimentalApis`，转正后进 `capabilities`。

没有把窗口当成一种岛上页面、沿用 `webview.postMessage`：页面的 id 是清单里的 `viewId`，可见性跟着岛屿走；窗口是运行时建的，生命周期不同，混在一起两边的规则都说不清。

## 5. 权限和护栏

- **新权限 `windows`**，普通权限，启用插件时授予。不设为「敏感」：敏感权限保护的是数据，这里没有新数据。
- **市场审核**：新版本第一次申请 `windows` 时暂缓上架，等维护者看（申请新权限本来就会暂缓）。市场和卡片上标「独立窗口」。
- **护栏**，都由岛屿的原生层执行，插件绕不过去：
  1. 浮层顶上有一条岛屿画的标题条，写着插件的图标和名字，页面盖不住它。
  2. 小组件不拿键盘焦点（第 3 节）。
  3. 浮层只能在用户刚操作过这个插件的 15 秒内显示或取得焦点（按过它的快捷键、点过它的命令或它的窗口），和 `island.openView` 用同一条规则（[reveal.rs](/src-tauri/src/plugin_host/reveal.rs)）。
  4. 窗口不进任务栏，系统标题固定带「· 浮屿」，页面改不了。
  5. 不能全屏盖住所有屏幕，不能跑到屏幕外，数量有上限（第 4 节）。
  6. 用户的三个开关（第 3 节）优先于插件的设置。
- **权限管不到的地方不变**：`.exe` 插件本来就能绕开岛屿自己建任何窗口。这套设计保证的是「经岛屿建的窗口，页面是隔离的、有这些护栏」，文档里照实写。

## 6. Mac

第一期只做 Windows，用户已同意。Mac 上 `window.*` 返回「这个系统暂不支持」，能力列表里没有 `windows`，卡片和市场提示「独立窗口暂不支持 Mac」（做法同 G1.16）。

和 G1.15 的关系：G1.15 研究的是把 WKWebView 叠到岛屿窗口上。独立窗口在 Mac 上反而简单一些，一个 `NSPanel` 里放一个 WKWebView，不用解决叠放和跟随位置。建议 G1.15 调研时把两种一起看：自定义 URL scheme 提供文件、`WKScriptMessageHandler` 做消息通道、`WKNavigationDelegate` 拦跳转、`WKContentRuleList` 拦请求。这部分要另起任务，不在本稿的工作量里。

## 7. 不用独立窗口能做到哪一步

启动台的简版今天就能做在岛上：命令加全局快捷键，`island.openView` 展开岛屿并打开插件的列表页，列表模板自带搜索框（`view.search`），回车触发条目动作。

| | 岛上的简版 | 独立窗口版 |
|---|---|---|
| 出现的位置 | 岛屿所在的位置（屏幕顶部） | 插件定，通常是屏幕中央 |
| 大小 | 岛屿面板的大小，列表 2 到 8 行 | 插件定 |
| 界面 | 列表模板，风格和岛一致 | 插件自己的网页，网格、图标墙都行 |
| 键盘 | 搜索框和上下选择由岛屿处理 | 页面自己处理 |
| 今天能不能做 | 能，Windows 和 Mac 都行 | 不能 |

用户已同意先做简版（任务 E33）：它是对照，也能验证用户是否真的需要屏幕中央那个大窗口。桌面小组件没有对应的简版，只能等独立窗口。

## 9. 原型的结果（2026-11-14，任务 E32）

**结论：通过，E34 可以开始。** 做法、每一项的原始结果和脚本要点见 [e32-plugin-window-prototype.md](/docs/investigations/e32-plugin-window-prototype.md)。

原型在仓库外的副本里做，没有进产品代码：隔离的应用标识下的 release 程序，建不经过 Tauri 的 `WS_POPUP` 顶层窗口，里面是原样的 `win32::webview_page`，环境从岛屿的 webview 拿。

| 项 | 结果 | 说明 |
|---|---|---|
| p8 第二轮的全部检查，浮层和小组件各一遍 | 通过 | 页面里没有任何调用岛屿命令的通道；本机 HTTP 服务器没有收到任何请求；越出入口文件夹的路径都是 404；跳转被取消 |
| 浮层的键盘焦点 | 通过 | 点击后能打字；原生层能在用户操作后给它焦点；后台新建时成不了前台，被系统的前台锁挡住 |
| Esc 和浏览器快捷键 | 通过 | `AcceleratorKeyPressed` 里处理 Esc，页面收不到这次按键；F5、F12 不刷新、不开开发者工具 |
| 透明和圆角 | 通过 | 窗口式宿主加 `WS_EX_NOREDIRECTIONBITMAP` 就是逐像素透明，还能叠加整体透明度；不透明底色配 DWM 圆角也正常。**不需要合成宿主** |
| 拖动 | 通过 | 页面发消息、原生层投递 `WM_NCLBUTTONDOWN`，浮层和小组件都能拖；CSS `app-region: drag` 要打开 `IsNonClientRegionSupportEnabled` 才生效 |
| 窗口页面和岛上页面的存储互相隔离 | **不成立** | 同一插件的页面共用 `localStorage`、Cookie、IndexedDB、Cache，能用 `BroadcastChannel` 通信。不同插件之间、和岛屿之间读不到 |
| 多开窗口的内存 | 通过 | 每个窗口一个渲染进程，约 21 到 26 MB；8 个约 200 MB；关掉后进程都退出 |
| 小组件收不到键盘输入 | **只靠 `WS_EX_NOACTIVATE` 不通过**，加一步后通过 | 岛屿自己的窗口是前台时点一下小组件，键盘输入就进了它的页面。原生层在窗口被激活时把激活和焦点还给原来的窗口，之后页面一个按键都收不到 |
| 小组件的鼠标点击 | 通过 | |
| 贴在桌面上的层级在「显示桌面」后可见 | 通过 | 把窗口的所有者设为桌面（`Progman`）：平时在别的窗口下面，Win+D 之后仍然可见、能点击。单纯放到最底的窗口在 Win+D 之后看不见 |

**对设计的修正**，E34 照此实现：

1. **小组件不拿焦点要由原生层保证（护栏 2）。** 窗口收到 `WM_ACTIVATE` 和 `WM_SETFOCUS` 时记下原来的活动窗口和焦点窗口，随后调用 `SetActiveWindow` 和 `SetFocus` 还回去，控制器的 `GotFocus` 里再做一次。原因是鼠标落在 WebView2 的子窗口上，是它决定激活，我们的窗口收不到 `WM_MOUSEACTIVATE`。所有者是桌面的小组件在桌面是前台时同样会被激活，同样靠这一步挡住。合成宿主挡不住，不用为这个换宿主方式。E34 的测试里要有「岛屿是前台时点小组件再打字」这一条。
2. **同一插件的页面共用存储和 `BroadcastChannel`。** 第 8 节「不做的」里写窗口之间不直接通信，实际上同一插件的窗口之间能通过 `BroadcastChannel` 通信，岛屿拦不住，也没有必要拦：它们本来就是同一个来源。文档里照实写。页面里的存储不落盘，所有插件页面都关掉后才清空，要留的数据用 `storage` 接口。
3. **透明用窗口式宿主**：窗口带 `WS_EX_NOREDIRECTIONBITMAP`，页面背景透明；`opacity` 用 `WS_EX_LAYERED`；点击穿透用 `WS_EX_TRANSPARENT`。页面里透明的像素仍然接收鼠标，做不出「只有某一块能点穿」的窗口，`clickThrough` 只能是整个窗口。
4. **贴桌面的层级用「所有者设为桌面」**，不是 `HWND_BOTTOM`。
5. **浮层在后台显示时拿不到前台**，这和护栏 3 的方向一致：`window.focus` 只在用户刚操作过时有效，失败时要有返回值告诉插件。
6. **浮层要接管 `WM_CLOSE`**（Alt+F4），默认处理会直接销毁窗口。
7. **`startDrag()` 用发消息的做法**，不依赖 CSS 拖动区。

**原型没有覆盖的**，留给 E34：输入法；多显示器和不同缩放之间移动；用户拉伸；前台是别的程序时小组件抢到前台的情况（测试里没有出现，对应的「把前台还给那个程序」没有验证）；从激活到把焦点还回去之间那一轮消息循环里的按键。

## 10. 新增的对外契约

转正时登记到 [contracts.md](/docs/architecture/contracts.md) 和插件文档；实验期间不算。

- 权限 `windows`，能力 `windows`。
- 方法 `window.create`、`window.update`、`window.show`、`window.hide`、`window.focus`、`window.close`、`window.list`、`window.postMessage`、`screens.list`。
- 通知 `window.message`、`window.bounds`、`window.focused`、`window.closed`、`screens.changed`。
- 页面接口 `close()`、`startDrag()`、`resize()`。
- `plugins.json` 每个插件多三个开关：不允许置顶、不允许点击穿透、隐藏全部窗口。
- 市场索引的审核规则不变（新权限本来就要审），标签多一个「独立窗口」。

## 12. 实现和本稿不一样的地方（2026-11-14，任务 E34）

代码在 `src-tauri/src/win32/plugin_window/`（原生窗口：标题条、层级、透明、小组件把焦点还回去、屏幕列表）和 `src-tauri/src/plugin_host/windows/`（参数校验和摆放 `spec.rs`、主线程上的窗口表和页面 `native.rs`、方法和通知 `mod.rs`）。示例插件在 `plugins/drafts/dev.focusd.window-demo/`：实验插件进不了签名的市场索引，所以不放 `plugins/examples/`。

| 本稿 | 实现 | 原因 |
|---|---|---|
| 坐标没说清 | 一律是物理像素的屏幕坐标；`bounds` 是整个窗口，浮层含标题条。`screens.list` 给每块屏幕的 `scale`；页面的 `resize(width, height)` 用页面的 CSS 像素，岛屿换算 | 窗口跨不同缩放的屏幕时，物理像素不会歧义 |
| 浮层和小组件都能透明 | 浮层不透明（主题底色、DWM 圆角、岛屿用 GDI 画的标题条），可以设整体 `opacity`；逐像素透明只给小组件 | `WS_EX_NOREDIRECTIONBITMAP` 的窗口上 GDI 画不出来，标题条就没了。小组件透明用原型里 tao 的做法（DWM blur-behind 加空区域），这样还能叠加 `opacity`（原型第 4 节） |
| 标题条有插件的图标和名字 | 只有名字和关闭按钮 | 插件图标可能是 SVG，GDI 画不了；名字已经够认出是谁的窗口。转正前再看要不要加 |
| 通知五个 | 多一个 `window.hidden { id, reason }`：浮层被 Esc 或失焦（`hideOnBlur`）收起时 | 插件要知道浮层不在屏幕上了，`window.focused` 分不清「失焦」和「被收起」 |
| `window.update` 多的合并 | 超过每个窗口每秒 30 次返回 429 | 合并要攒着延后执行，实验期间先简单处理 |
| 「用户刚操作过」 | 除了快捷键、命令、提示按钮、链接，还算：点浮层的标题条、点击激活浮层、拖动窗口、页面调用 `startDrag()`、页面发消息时鼠标就在这个窗口上且 1.5 秒内有键鼠输入 | 页面里的脚本能自己发消息，单凭「页面发了消息」就算的话，常驻的小组件可以一直给自己续上 15 秒 |
| `screens.changed` 发给订阅的插件 | 发给有窗口的插件，先把窗口挪回屏幕内再发 | 不用新增订阅事件；没有窗口的插件用不着它 |
| 页面的主题跟着岛屿 | 语言和颜色取岛上最近一次打开插件网页页面时的值，默认中文、深色 | 岛屿的主题只在前端，原生层没有；要实时跟随得加一条前端到原生的通知，转正前再做 |
| 页面接口同网页页面 | 窗口页面的 `getState()` / `setState()` 不保存 | 窗口由插件建和关，状态归插件自己用 `storage` |
| 关闭的原因 | `window.closed` 的 `reason`：`user`（关闭按钮或 Alt+F4）、`page`（页面 `close()`）、`hidden`（用户在设置里隐藏）、`failed`（页面建不起来）；插件自己 `window.close` 不发；进程退出时窗口全关，不发 | 进程已经没了，发了也收不到 |
| 贴桌面的层级用「所有者设为桌面」（第 9 节修正 4） | 照做，另加一步：小组件被激活时（点击、拖动），Windows 会把它的所有者 Progman 连同小组件一起提到所有程序上面，看起来像按了 Win+D，而且松手后不会自己回去。所以小组件被激活、而激活前前台不是桌面本身时，原生层把 Progman 放回最下面那个普通程序窗口的下方；激活前前台是桌面（刚按过 Win+D）就不动。在 `WM_WINDOWPOSCHANGING` 里直接去掉 Z 序变化不行：那样 Win+D 时小组件也跟不上桌面了，而两种情况下小组件收到的 `WINDOWPOS` 一模一样（实测）。拖动期间不把焦点还回去，松手后再还，否则激活来回切换，原来的窗口会闪。还有一处：小组件被激活过一次，就成了 Progman「最近激活的弹出窗口」，之后 Win+D 激活桌面时，系统转而激活小组件，桌面没成为前台，再按 Win+D 也不恢复窗口（实测）。所以小组件不是被鼠标点中而被激活时，直接 `SetForegroundWindow(Progman)`：这样不会被转走，也清掉了那条记录 | 真岛验收时发现（2026-11-14） |
| 设置里的三个开关 | 在插件详情页「窗口」一节，只对申请了 `windows` 权限的插件显示；存在 `plugins.json` 每个插件的 `windowRules`（`noTopmost`、`noClickThrough`、`hidden`）。不允许置顶时，`topmost` 当 `normal`；隐藏时关掉它的全部窗口并拒绝新建 | |
| Mac 上返回「暂不支持」 | 返回 501；`initialize.experimentalApis` 里没有 `windows`。实验通道本来就只在开发模式下，市场里没有用它的插件，所以卡片和市场的提示等转正时一起做 | |

**护栏怎么验证**：第 1 条（标题条在页面上方）、第 4 条（标题后缀）、第 5 条（不出屏幕、不大过工作区、数量上限）、第 6 条（用户开关优先）有单元测试（`plugin_host/windows/tests.rs`、`win32/plugin_window` 的测试）；第 3 条用的是和 `island.openView` 同一个判断，有测试；第 2 条（小组件拿不到键盘）和「Esc、Alt+F4、拖动、显示桌面、停用插件后没有残留窗口和 WebView2 进程」要在 Windows 真岛上实测，记录写在 E34 的任务文件里。

**还没做的**：输入法、用户拉伸后页面的重新布局以外的细节、显卡重置和休眠后的恢复都没有专门测；「把前台还给别的程序」的分支照原型的做法写了（`SetForegroundWindow`），仍没有遇到需要它的情况。
