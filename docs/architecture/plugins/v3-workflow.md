## 为什么不开分支

| 做法 | 问题 |
|---|---|
| 开一个长期分支做完再合 | 第 3 版要四五个月，几乎碰到全部前端。这期间 `main` 上别的会话每天都在改同样的文件，分支越走越远，最后合不回来。仓库规则也不允许在主工作区切分支：你的 `pnpm tauri dev` 和别的会话都在这份代码上 |
| 另开一个仓库重写 | 等于同时维护两个浮屿；Rust 层和 Mac 适配要一直手动同步 |
| **在 `main` 上做，藏在开关后面** | 每一步都小，随时能合入、能发版、能回退；别的会话照常工作。代价是有几个月新旧两套并存 |

具体怎么藏：

| 阶段 | 新东西对用户可见吗 | 开关 |
|---|---|---|
| 0 可行性验证 | 不在仓库里 | — |
| 1 内核 | 默认关。宿主进程不启动，行为和现在完全一样 | 一个开发用的开关（环境变量或 `plugins.yml` 里的一项），开发版默认开 |
| 2 插槽化 | 没有开关：这是纯搬迁，零行为变化，靠回归页和真岛验收保证 | — |
| 3 内置功能插件化 | 每个功能迁完后，先在测试通道（beta）的版本里默认开，正式通道晚一个版本 | 同一个开关，逐步改成默认开 |
| 4 接缝 | 同上 | |
| 5 第三方插件 | 新市场和安装入口随 0.4.0 一起出现 | |
| 6 下线第 2 版 | 删除旧代码。**唯一不能靠开关回退的一步**，所以放在第 3 版默认开满一个完整的发版周期之后 | — |

## 代码放哪

原则如下；具体的名字第 1 阶段开头（2026-11-15）定了：

| 东西 | 定下的位置和名字 |
|---|---|
| Cordis | `vendor/cordis/<包>/`：`core`（npm 名 `cordis`）、`loader`、`hmr`、`include`、`fs`、`fs-node`。拷的是 npm 上的构建产物，不用构建；`pnpm-workspace.yaml` 的 `overrides` 把全仓对这些包的引用都指到这里 |
| 基座的 TS 包 | `packages/plugin-base`，npm 名 `@fuyu/plugin-base`（私有，不发布）。`.` 是插件用的接口，`./host` 是宿主。公开发布时再定正式的名字 |
| 基座的 Rust 部分 | `src-tauri/crates/plugin-base`（crate 名 `plugin-base`）。`src-tauri/Cargo.toml` 加了 `[workspace]`，它是成员也是默认成员：工作区的根仍是 `src-tauri`，构建目录不变，`cargo test`、clippy 不加参数就连它一起跑。不依赖 `src-tauri` 的模块、不写 `unsafe`，作业对象和进程组经 `Containment` 由浮屿提供 |
| 插件接口包 `fuyu-plugin` 2.0 | 第 5 阶段。第 1 阶段插件用 `@fuyu/plugin-base`；宿主把要共享的包名都指到同一份内核，所以以后加 `fuyu-plugin` 这个名字只是多登记一个别名 |

原则：

| 东西 | 位置 | 规则 |
|---|---|---|
| 拷进来的 Cordis | `vendor/` | 不受行数和「不写注释」的约束；`vendor/README.md` 记上游版本、提交号、本地改动 |
| 基座的 TypeScript 包（内核包装、宿主入口、插槽、命令行工具） | `packages/` 下新建的包 | 不能 import `src/` 里的任何东西，lint 检查 |
| 基座的 Rust 部分（看管宿主、管道、「标记即服务」的宏） | 独立的 crate，和 `src-tauri` 组成一个 Cargo 工作区 | 不能依赖 `src-tauri` 里的领域模块；`unsafe` 的规则照旧 |
| 浮屿自己的内置插件 | `src/` 下，按现有的 `features/` 逐个改造 | 遵守 `src/AGENTS.md`；第 3 阶段开头更新它的目录地图和分层规则 |
| 第 2 版的 SDK `packages/fuyu-plugin` 1.x | 原地不动 | 冻结；新的 2.0 在新的包里开发，第 6 阶段替换 |
| 第 0 阶段的临时代码 | 仓库之外 | 不合入 |

## 每个阶段怎么走

**开头**
1. 读 [v3-progress.md](v3-progress.md) 和方案里这个阶段的内容、验收，把它拆成步骤。步骤写进这个阶段各子任务的「验收」里（一个会话只改自己的任务文件，不会互相冲突），做完一步勾一步；`v3-progress.md` 的阶段表只在阶段开头和结尾改。
2. 认领子任务，写 `scope`；在 issue 下回复谁接手、打算怎么做。
3. 量这个阶段开始时的基线（内存、冷启动），记进计划。

**中间**
- 提交：一个可验证的单元一个提交；**搬迁和改写分开提交**，搬迁的提交零行为变化；只提交自己的文件。
- 合入：攒成一批用 `pnpm mq:land`，条件照旧（一个子任务做完、5 个提交以上或最早的超过 6 小时）。不攒到阶段结束才合：小步合入，别的会话才能跟上。
- 每次合入前按改动范围验证：

| 改了什么 | 要跑的 |
|---|---|
| 基座的 TypeScript 包、前端 | `pnpm check` + `pnpm build`；动了界面再加 `pnpm test:regression` |
| Rust（含基座的 crate） | `cargo test` + `pnpm build:exe` |
| 内核 | 再加：保证清单的测试、反复加载卸载的测试 |
| 宿主进程、通信 | 再加：杀掉宿主后恢复的测试 |

**结尾**
1. 跑一遍这个阶段的验收，把实测的数字写进计划。
2. **真岛验收**：Windows 和 Mac 各一次，由你来看，我列出要看的每一项。没看过的如实标「待人工验收」，不算做完。
3. 同步文档：`AGENTS.md` 的目录地图、`overview.md`、`contracts.md`、`platforms.md`，以及 [v3-progress.md](v3-progress.md)（阶段表、实测数字、风险现状）。它没更新，这个阶段不算做完。
4. `pnpm tasks done`，在 issue 下回复改了什么、提交、验证结果，关闭。
5. 如果这个阶段要改变默认开关：先发一个测试通道的版本，观察没问题再进正式通道。

## 并行开发

第 3 版会同时有三种并行：几个会话一起做、一个会话里开子代理、Mac 和 Windows 两台机器同时做。三种的规则不一样。

### 几个会话一起做

- **内核和基座的包由一个会话负责**。别的会话要改它们的接口，先在任务里写明或发消息商量，不直接改。
- **第 2、3 阶段可以并行**：每块界面、每个功能是一个子任务，一个会话认领一块，`scope` 互不重叠。认领以任务文件为准（看本地和 `origin/main`），不等别的会话回消息。
- **正在被改造的功能暂时不接别的活**：某个功能的子任务被认领期间，别的会话不在它的目录里做功能开发（`pnpm tasks conflicts` 会提示）。没轮到的功能照常开发。
- **新功能的写法**：第 1 阶段做完之后，新开的功能直接按插件的结构写，不再往旧结构里加。
- **改公共定义要单独先合入**：插槽的定义、服务的类型、清单格式会影响所有用它的插件。改定义的那个提交单独合入，别的会话同步之后再改使用方。改之前在任务里写明，或者发消息告知。
- **进度各记各的**：每个会话只改自己认领的任务文件；[v3-progress.md](v3-progress.md) 里每一节由谁改有规定，免得几个会话同时改同一行。

### 一个会话里开子代理

子代理是会话为了并行而开的帮手，它不是独立的开发者：

| 事 | 谁做 |
|---|---|
| 认领任务、在 issue 下回复 | 只有会话自己 |
| `git commit`、`pnpm mq:land`、关 issue、发 npm 包、任何对外的动作 | 只有会话自己 |
| 改 `v3-progress.md`、任务文件、公共定义 | 只有会话自己 |
| 调研、读代码、找用法、写一份草稿 | 可以交给子代理 |
| 改代码 | 可以，但每个子代理只改会话分给它的那几个文件，文件互不重叠，而且都在会话认领的 `scope` 之内 |
| 构建和测试 | 轻的（单个测试文件）子代理可以跑；`cargo` 的构建和测试、`pnpm check` 由会话自己统一跑一次，几个子代理同时构建会互相抢同一个构建目录 |

- 子代理和会话在同一份工作区里（仓库不许开 worktree），所以分给它们的文件必须不重叠；会话在它们干活时也不动这些文件。
- 子代理交回来的是报告，不是证明：会话自己看改动、跑验证，再提交。
- 适合拆给子代理的：互不依赖的几个功能各搬一份、给一批文件做同样的机械改动、同时查几份资料。不适合的：改同一个文件、前后有依赖的步骤、要判断设计取舍的事。
- 一次开很多子代理（几十个）的编排，只有你明确要求时才用。

### Mac 和 Windows 同时做

两台机器各有一份本地 `main`，只通过 `origin/main` 互相看到对方的改动。开工和合入前同步、认领怎么区分机器、同一个任务不两台同时做、两边共用的代码、交接写进任务文件，这几条通用规则见 [workflow.md](../workflow.md)「两台机器」；下面只列第 3 版特有的。

| 情况 | 规则 |
|---|---|
| **平台专有的代码** | `win32/` 只在 Windows 上改和验证，`macos/` 只在 Mac 上。这两处天然不冲突，适合两台机器并行 |
| **只有一台机器能做的事** | Windows：官方签名私钥、WebView2 的实测、Windows 安装包。Mac：公证、WKWebView 的实测。任务的 `scope` 或说明里写明在哪台做；只有你本人能做的标 `needs: user` |
| **实测和验收** | [v3-progress.md](v3-progress.md) 里每个系统各占一行，在哪台机器上测的就改哪一行，两台机器不会改到同一行 |
| **公共定义变了** | 改定义的提交先单独合入；另一台机器同步之后，再在上面继续做。不要两台机器同一天都改同一个公共文件 |
| **宿主用的 Node 程序** | 每个系统一份，不放进 git（太大）。由脚本按固定的版本和哈希下载，第 1 阶段定 |

第 0 阶段的临时项目也要两台机器都能跑，所以放在一个私有的 GitHub 仓库里最方便（建仓库要你同意）。

## 第 0 阶段具体怎么做

- **时间**：一周，到点就出报告，没测完的写「未测」和原因，不拖。
- **地方**：仓库之外的临时项目，一个最小的 Tauri 应用。
- **做什么**：方案第 0 阶段列的 8 项，按风险从高到低做，前 3 项决定架构能不能成立：
  1. Node 和 Bun 各当一次宿主：Cordis 的内核、加载器、热重载能不能跑；内存、启动时间、安装包增量。
  2. 附带程序的打包和签名。
  3. 窗口到宿主的本机 WebSocket 通不通。
- **产出**：`docs/investigations/v3-feasibility.md`。每一项写：怎么测的、在哪个系统上、数字、结论（成立 / 有条件成立 / 不成立）、对方案的影响。
- **之后**：我把报告和「要不要改方案」的建议给你，你定继续、改方案还是停。前 3 项里有不成立的，先改方案再做第 1 阶段。
- **临时代码**：报告合入后留在原地备查，不进仓库；里面有用的片段到第 1 阶段重新写进基座的包里。

## 发版

- 第 0–4 阶段期间，浮屿照常按 0.3.x 发版；第 3 版的东西要么不可见，要么在开关后面。
- 开关默认打开的变化先走测试通道。
- 第 5、6 阶段合成 0.4.0：新的市场、第三方插件、删除第 2 版。发布说明要写清楚旧插件会失效，以及重写后的官方插件在哪。
- 基座的公开发布不跟浮屿的版本走：满足方案「基座做成开源项目」里的条件就发。
