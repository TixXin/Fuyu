# 审核看什么

> 分档的条件和审核分析器 [`packages/plugin-review`](../../packages/plugin-review/README.md) 的实现一致，分析器改了这一页跟着改。市场 CI 在 `TixXin/fuyu-plugins`（[#25](https://github.com/TixXin/fuyu-plugins/pull/25) 合入），提交流程见[发布](publish.md)。

## 每个版本都审

- 不只审第一次上架。每个版本在 `fuyu-plugins` 都是一个 PR：市场 CI 从你交的提交号取源码、构建，跑审核分析器，把报告贴进 PR。
- **每个版本都要维护者点批准才上架，绿档也一样。** 维护者可能先让 AI 读差异、写一份审核意见，但那只是草稿，不能代替人批。市场 CI 里不跑大模型。
- 新版本和**上一个审过的版本**比。
- 第一次上架没有旧版本可比，至少是黄档，维护者通读全部源码。换密钥、换人、换仓库也按第一次上架审（见[市场规则](market-rules.md#换密钥换人换仓库)）。

## 三档

| 档 | 什么时候 | 怎么处理 |
|---|---|---|
| 绿 | 和上一个审过的版本比，下面黄档、红档的条件一条都没命中 | 维护者看报告的摘要和差异，点批准 |
| 黄 | 命中[黄档](#黄档)的任何一条 | 维护者逐项看，必要时请你说明。黄档不等于拒绝：说清楚了、确实需要的照样批准 |
| 红 | 命中[红档](#红档)的任何一条 | CI 直接失败，不进人工审核；改好后重新提交 |

### 黄档

| 检查 | 什么算 |
|---|---|
| 首次上架 | 没有旧版本可比 |
| Node 内置模块 | 新用到的 Node 内置模块：`import`、`require`、`import()` 里写死的模块名，`node:fs` 和 `fs` 都算；清单里有 `fuyu.nodeApis`（构建时写入）时，代码用到了、它里面却没有的 |
| 联网 | 代码里新出现的域名；没在 `fuyu.network` 里声明的域名；由字符串拼接得到的域名（`"api." + "example.net"`、`["api", "example", "net"].join(".")` 也会被合起来看）；`fuyu.network` 新声明的域名 |
| 依赖 | `package.json` 里新增、删除、改了范围的依赖；锁文件（`package-lock.json` 或 `pnpm-lock.yaml`）里新增、删除、换了版本的包，同一版本内容哈希或下载地址变了的，带安装脚本的；有依赖却没有锁文件；`package.json` 的安装脚本（`preinstall`、`install`、`postinstall`、`prepare` 等）变了。**依赖的任何变化都算黄**：靠更新下毒常常藏在依赖升级里 |
| 敏感调用（同一个文件里比旧版多了） | `child_process`、`vm`、`eval` / `new Function` / 字符串形式的 `setTimeout`、`process.binding` / `dlopen`、模块名不是写死的 `import()` / `require()`、用户主目录 / 临时目录 / 系统环境变量（`HOME`、`USERPROFILE`、`APPDATA` 等）里的路径、绝对路径、带 `..` 的路径、浮屿或别的插件的数据目录、运行时拼出来的网址 |
| 像混淆的（比旧版多了） | 超过 1000 个字符的行、大块 base64 或十六进制、高熵的长字符串 |
| 清单 | `fuyu.provides`、`fuyu.replaces` 有增删 |
| 文件 | 新的或改过的脚本文件（`.sh`、`.ps1`、`.bat`、`.cmd`、`.vbs`、`.applescript` 等）、认不出的二进制文件、符号链接 |
| 改动量 | 文本文件逐行比较（不算锁文件），增删合计超过 300 行 |

### 红档

审核分析器查的：

| 检查 | 什么算 |
|---|---|
| 原生扩展 | 任何 `.node` 文件 |
| 可执行程序 | 按扩展名（`.exe .dll .so .dylib .com .scr .msi .app .bin .elf .jar .wasm`）或文件头（PE、ELF、Mach-O、WebAssembly）认出来的文件 |
| 混淆 | 3 个以上不同的 `_0x…` 风格变量名；`fromCharCode` 连着 8 个以上数字拼字符串；一行里 `\x` / `\u` 转义有 8 个以上、占这一行的四成以上 |
| 实验接口 | 清单的 `fuyu.experimental` 不为空 |
| 清单 | 读不到 `package.json`，或者它不是 JSON 对象 |

### 不分档、直接让检查失败的

市场 CI 在分档之外还查这些，不过就不上架：

- 作者签名验不过，或者签名的密钥不在提交文件的 `authorKeys` 里；提交文件里改了已经上架的那一行，或者没有权限的改动（见[发布](publish.md#提交文件)）。
- `package.json` 的 `name`、`version`、`repository` 和提交文件里那一行对不上。
- 依赖不符合市场构建的要求：只收 `package-lock.json`，依赖都来自 npm 官方源并带 `sha512` 校验（见[发布](publish.md#上架之前)）。审核分析器也读得懂 `pnpm-lock.yaml`，但市场构建不收它。
- 构建失败：清单校验不过（名字的作用域和仓库所有者对不上、用了 `@fuyu/*`、缺 `engines.fuyu`、`license` 是 `UNLICENSED`、用了实验接口等，规则见[清单和安装包](package.md)），或者打出的包不符合[包的限制](package.md#包里不能有的)。
- 源码里扫出遗留的密钥（令牌、API 密钥、私钥）。

新加的作者密钥没有旧密钥签的换密钥证明时不会让检查失败，但报告里会标出来，维护者按重新上架看待（见[市场规则](market-rules.md#换密钥换人换仓库)）。

### 分析器的局限

- 它只用正则加轻量的词法扫描（先去掉注释，认出字符串、模板字符串和正则），不解析代码，所以会漏报，也会误报。分档只是给维护者的提示，绿档也要人看过差异才批。
- 源码和构建产物都能扫。像混淆的那几项只看源码，因为构建产物本来就是压缩过的。
- 敏感调用和像混淆的长字符串按「这个文件里比旧版多了几处」算，原来就有、数量没变的不再报。

## 冷静期

- 新版本**上架 3 天后**才自动更新到用户那里。从市场上架的时间（索引里的 `publishedAt`，由市场 CI 写）算，不从你打标签或提交的时间算。
- 冷静期只管自动更新：用户在插件页手动点更新可以立刻装，确认框会写「这个版本上架不到 3 天」。
- 新安装也默认装过了冷静期的最新版；插件只有冷静期内的版本时（刚上架）照装，标「刚上架」。
- **`urgent`（立即推送）**：修安全问题这类等不了 3 天的版本，在 PR 里说明，**由维护者决定标不标**，作者自己不能标。标的时候必须写中英文原因，岛屿的更新说明里会显示这个原因。标了的版本不等冷静期就自动更新。

另外几种版本不会自动更新：被撤销成 `warn` 的；预发布版（版本号带 `-beta.1` 这类标记，默认跳过）；作者或签名密钥换了的（要用户确认）。市场索引 7 天过期，市场每天重签一次；索引过期时浮屿暂停自动更新和新安装，已经装了的插件照常运行。

冷静期管得住的是给别人留出发现问题的时间，管不住潜伏期比 3 天长的问题。

## 提交前先自查

作者提交前就能看到自己落在哪一档，用命令行 `fuyu-plugin`（怎么运行见[命令行](cli.md#怎么运行)）：

```bash
fuyu-plugin review <上一个上架的提交> HEAD
```

- 两边可以是 git 提交（提交号、标签）或文件夹；第一次上架没有旧版本，旧的一边写 `-`。
- 报告和市场贴进 PR 的是同一个分析器、同一种格式，列出命中的每一条检查和文件、行号。
- 红档时退出码是 1，绿档和黄档是 0。其余选项见[命令行](cli.md#review)。

只想看这一个版本有没有会被拦的东西，跑 `fuyu-plugin check --market`：它试构建一次，把红档的项当错误、对作者有用的黄档项当告警报出来（见[命令行](cli.md#check)）。

不装命令行也能在浮屿仓库（[`TixXin/fuyu`](https://github.com/TixXin/fuyu)）的根目录直接跑分析器，比较两个源码文件夹，只要 Node 22.15 或更新：`node packages/plugin-review/src/cli.mjs <旧文件夹 | -> <新文件夹>`。

## 怎样更快通过

- 一个版本只做一件事。依赖升级单独发一个版本，在 PR 里写为什么升。
- 新加域名、新用 `child_process` 或新的 Node 模块时，在 PR 里写清用途。
- 带上锁文件；不要把压缩过的第三方代码拷进源码。
- 图片、字体放进 `assets/`，用常见的格式（PNG、SVG、WOFF2 等），不要写成代码里的 base64 长字符串。
