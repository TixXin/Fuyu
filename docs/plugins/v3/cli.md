# 命令行

> **提纲。** 第 3 版的命令行是 `fuyu-plugin` 2.0，还在做（[#483](https://github.com/TixXin/fuyu/issues/483)）。这一页先列计划中的命令和已经定下的行为，安装方式、参数和输出等它合入后补，缺的列在[待补](#待补)。第 2 版的插件继续用 `fuyu-plugin` 1.x 的命令，见[第 2 版的文档](../README.md)。

## 命令一览

| 命令 | 做什么 | 状态 |
|---|---|---|
| `build` | 构建插件：宿主部分和各窗口的界面部分分别打包，扫出 `nodeApis` 写进清单 | 在做 |
| `pack` | 把构建结果打成 `.fuyu` | 在做 |
| `check` | 不运行插件的静态检查：清单、声明和代码是否对得上 | 在做 |
| `review` | 比较两个版本，给出绿 / 黄 / 红三档和理由 | 在做；分析器已经能单独跑 |
| `keygen`、`sign` | 生成作者签名密钥；给提交号签名 | 在做 |
| `publish` | 打标签、给提交号签名、向市场开 PR | 计划 |
| `dev` | 接上正在运行的浮屿：从文件夹加载插件、改了代码自动重载、看占用 | 等第 2–4 阶段 |

## build

- 宿主部分（`fuyu.host`）按 Node 打包，npm 依赖全部打进这一个文件。
- 各窗口的界面部分（`fuyu.client`）按浏览器打包：`react`、`react/jsx-runtime` 不打进去，改写成浮屿提供的转接模块的相对地址；样式打进 JS。
- 扫出宿主部分用到的 Node 内置模块，写进清单的 `fuyu.nodeApis`；同时写入 `fuyu.builtWith`。
- 对照代码检查清单里的声明（`inject`、`provides`、`slots`、`commands`、`network` 等）。
- **市场构建用的是同一个 `build`**，只是构建配置由市场提供。所以在自己电脑上构建通过，基本就能在市场构建通过。

## pack

- 打出 `<作用域>-<名字>-<版本>.fuyu`。
- 同样的文件永远打出逐字节相同的包，同一份源码两次构建、打包的哈希相同。
- 包里不能有的东西（`node_modules`、`.node`、可执行程序等）打包时就会拒绝，规则见[清单和安装包](package.md#包里不能有的)。

## check

不运行插件，检查清单的必填项、名字、`engines.fuyu`、路径，以及声明和代码是否对得上。清单里不认识的字段给告警，不报错。

## review

```bash
fuyu-plugin review <旧提交> <新提交>
```

调用市场用的同一个审核分析器，结果和市场贴进 PR 的报告一样。分档条件见[审核看什么](review.md)。命令行做完之前，可以在浮屿仓库里直接跑分析器：

```bash
node packages/plugin-review/src/cli.mjs <旧版本目录 | -> <新版本目录>
```

退出码：0 是绿档或黄档，1 是红档，2 是参数或读取出错。

## keygen 和 sign

- Ed25519。第 2 版的作者签名密钥可以直接用。
- 上架市场时签的是**提交号**：`fuyu-plugin-commit/1`，加上插件名、版本、仓库、提交号，每样一行。
- 手动分发的 `.fuyu` 也可以签，签的是包的摘要；签名放进包里的 `fuyu-signature.json`，不改变包的内容。

## publish

计划是一条命令完成：给这个版本打标签、用作者密钥给提交号签名、向 `TixXin/fuyu-plugins` 开 PR。流程见[发布](publish.md)。
