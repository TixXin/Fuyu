# 插件平台第 3 版：第 0 阶段可行性实测

2026-11-14，会话「插件平台第 3 版基线和可行性验证」，任务 [E36.0](/docs/tasks/E/E36.0.md)（#290）。方案见 [v3-everything-plugin.md](../architecture/plugins/v3-everything-plugin.md)。

**在 macOS 上，方案的架构成立。** 前 3 项（Node 当宿主、附带程序的打包签名、窗口到宿主的本机 WebSocket）都跑通了，没有需要改架构的地方。**Windows 上一项都没测**，公证没测，所以这份报告只能回答一半。

## 1. Node 和 Bun 当宿主

### 怎么测的

`host/` 里一个最小的宿主：`ctx.use` 文件系统服务和加载器，再让加载器读一份 `cordis.yml`（做法照 Cordis 自带的命令行入口）。两个插件：`counter` 提供一个服务，`demo` 依赖它，注册一个受管的定时器和一个事件监听。配置里故意把 `demo` 写在 `counter` 前面。

### 能不能跑

| 项目 | Node 26.13.1 | Bun 1.4.4 |
|---|---|---|
| 内核、服务、依赖顺序（`demo` 等 `counter` 就绪才启动） | 通过 | 通过 |
| 加载器按 `cordis.yml` 加载插件 | 通过 | 通过 |
| 改配置文件就停用、启用、换配置、移除插件 | 通过，写文件后 3 ms 撤掉副作用 | 通过，15 ms |
| 热重载（改插件源码，自动换成新代码） | 通过，要 `--expose-internals` | **不能用**：热重载服务起不来，也不报错 |
| 装在宿主目录之外的插件 `import` 内核包 | 默认找不到；加一个解析钩子后通过，拿到的是同一份内核 | **没跑通**，见下 |
| 带 `--disallow-code-generation-from-strings` | 加载器直接报错，改 6 行后通过，见下 | 没有对应的开关 |

热重载的数字（Node，带 `--expose-internals`）：

- 改文件到新代码生效 48 ms。
- 连续重载 200 次：0 次失败，每次约 39 ms；受管的定时器数一直是 1（旧的都撤掉了）；`counter` 服务的状态保留。
- 强制回收后 JS 堆每次重载涨约 12 KB，200 次后进程的常驻内存多了 19 MB。和方案里「重载会留下旧模块，靠重启宿主回收」的判断一致。

### 四个要写进方案的发现

**一、正式使用不需要 `--expose-internals`。** 加载器拿不到 Node 内部的模块加载器时会退回普通的 `import()`，插件照常加载；只有热重载必须要内部接口。所以这个参数只在开发模式加，正式版不带。方案「风险」里「加载器要用 Node 的内部接口，Node 升级时可能失效」因此只影响开发模式。

**二、`--disallow-code-generation-from-strings` 和加载器冲突。** `@cordisjs/loader` 在模块顶层用 `new Function` 建了一个求值器（给配置文件里的表达式用），带这个参数时整个加载器 `import` 就失败：

```text
EvalError: Code generation from strings disallowed for this context
    at @cordisjs/loader/lib/index.js:24
```

把这个求值器改成用到时才建（6 行），加载器、热重载都正常了（冒烟测试和 30 次重载都过）；代价是配置里不能写表达式，浮屿本来也不用。Cordis 是拷进 `vendor/` 的，这个改动记进 `vendor/README.md` 的本地改动里。内核、热重载、配置文件这几个包里没有别的 `eval` 或 `new Function`。

**三、插件怎么找到内核，方案里没写。** 插件的宿主部分要 `import 'fuyu-plugin'` 拿到 `Service` 这类运行时的值，而它装在 `~/.fuyu/plugins/<名字>/`，旁边没有 `node_modules`。实测：

- Node 不做处理时，这个插件**不加载，也不报错**：它在加载器里只是一个没有状态的条目。这正是方案担心的「某个功能悄悄没了」。
- Node 用 `module.registerHooks` 加一个解析钩子，把这个包名指到宿主自己的那一份：插件加载成功，拿到的 `Context` 和宿主的是同一个，热重载也照常。
- Bun 默认会**自己联网从 npm 装一份**（它把 `cordis` 下载到了 `~/.bun/install/cache`），插件拿到的是另一份内核，`instanceof` 对不上。加 `--no-install` 关掉后，用 `Bun.plugin` 做同样的指向没有生效，插件不加载。

**四、出错是静默的。** 上面两处失败（热重载服务起不来、插件 `import` 失败）在没装日志服务时什么都不打印。第 1 阶段的状态视图和日志要先做，不然调试很费劲。

### 内存

单独跑宿主，启动 6 秒后读一次：

| 状态 | Node | Bun |
|---|---|---|
| 空进程 | 13.1 MB | 5.4 MB |
| 内核、加载器、两个插件 | 23.5 MB | 16.7 MB |
| 再加热重载（监听文件） | 25.3 MB | — |
| 再加 WebSocket 服务 | 28.3 MB | 18.3 MB |

放进 Tauri 应用里（宿主打成单个文件：内核、WebSocket 服务、心跳），闲置 15 秒后采样 20 秒：

| 配置 | 整个应用 | 宿主那一个进程 |
|---|---|---|
| 不带宿主 | 75.5 MB | — |
| Node 宿主 | 95–99 MB | 21.9–22.6 MB |
| Bun 宿主 | 89.8 MB | 13.8 MB |
| 隐藏 WebView 当宿主 | 90.8–91.7 MB | 13.8–14.2 MB（多出来的那个网页进程） |

空的 Node 进程 13 MB，和方案里引用的 Raycast 的 12 MB 对得上。这里只有两个演示插件；内置功能都变成插件之后是多少，要到第 1、3 阶段量。

### 启动时间

| 量什么 | Node | Bun |
|---|---|---|
| 进程启动到退出（什么都不做），15 次的中位数 | 32 ms | 14 ms |
| 进程启动到两个插件都跑起来 | 84 ms | 65 ms |
| 应用里：Rust 拉起宿主到 WebSocket 能连（平时） | 51–82 ms | 26–89 ms |
| 应用里：**装好后第一次启动** | **3170 ms** | **7383 ms** |

最后一行只出现在那个可执行文件第一次运行时，第二次启动就回到几十毫秒。推断是系统第一次运行一个新的大文件时要做的检查，没有进一步确认。对方案的含义：**岛屿不能等宿主就绪才显示**，更新后的第一次启动宿主会晚几秒。方案的启动顺序（先起岛屿必需的，再起其余的）要把这一点算进去。

### 安装包

| 文件 | 大小 |
|---|---|
| Node 26.13.1 的可执行文件（macOS arm64） | 140.5 MB；去掉符号后 104.6 MB，仍然能跑 |
| Bun 1.4.4 的可执行文件（macOS arm64） | 84.6 MB |
| Node 的 `node.exe`（Windows x64，官网的大小，没下载） | 95.5 MB |
| 宿主的 JS（内核、加载器、配置文件、文件系统服务打成一个文件） | 215 KB，压缩后 51 KB |

同一个应用分别打包（zlib 压缩的 dmg，和 Tauri 默认的一样）：

| | 不带宿主 | 带 Node | 带 Bun |
|---|---|---|---|
| dmg | 2.9 MB | 46.4 MB（+43.6） | 43.5 MB（+40.6） |
| dmg，改用 LZMA 压缩 | 2.0 MB | 33.0 MB（+31.0） | 31.5 MB（+29.5） |
| 更新包 `.app.tar.gz` | 2.8 MB | 44.8 MB（+42.0） | 41.3 MB（+38.5） |

浮屿现在的 dmg 是 13.0 MB，带上 Node 之后约 57 MB。去掉符号能再省约 5 MB（单独 gzip 后 38.1 MB 对 42.6 MB）。Windows 的安装程序会多多少没测。

### 结论

- **Node：成立。** 内核、加载器、热重载原样可用，内存在验收线内。
- **Bun：不建议。** 内存少 8–10 MB、可执行文件小 56 MB，但压缩后安装包只小 3 MB；热重载不能用，装在别处的插件拿不到同一份内核，默认还会自己联网装包。决定 12 的条件是「只要小改就能跑而且内存明显更低」，两条都不满足。

## 2. 附带程序的打包和签名

### 怎么测的

Node 作为 Tauri 的附带程序（`bundle.externalBin`），`signingIdentity` 设成 `-`（临时签名），授权文件里只写一项 `com.apple.security.cs.allow-jit`。另外单独拿 Node 的可执行文件试了几种签名组合。

### 结果

| 签名方式 | 结果 |
|---|---|
| Node 官方的签名（Developer ID，加固运行时，6 项授权） | 能跑 |
| 临时签名，不开加固运行时 | 能跑 |
| 临时签名，开加固运行时，**不带授权** | **启动就崩**：`Fatal process out of memory: Failed to reserve virtual memory for CodeRange`，退出码 133。加 `--jitless` 能跑 |
| 临时签名，开加固运行时，只带 `allow-jit` | 能跑，即时编译和 WebAssembly 都正常 |

打包出来的应用：

- 附带程序放在 `Contents/MacOS/node`。Tauri 把它重新签了名：临时签名、开了加固运行时（`flags=0x10002(adhoc,runtime)`），并且**带上了应用的那份授权文件**。`codesign --verify --deep --strict` 通过。
- 在这个包里，宿主在加固运行时下跑完了全部自动测试。
- `spctl` 判定为拒绝，这是临时签名的预期结果，不说明问题。

### 结论：有条件成立

- 要给浮屿的 `Entitlements.plist` 加 `com.apple.security.cs.allow-jit`（现在只有 `apple-events` 一项）。官方 Node 带的另外 5 项授权，这次测到的范围里用不上。
- **公证未测**：没有 Developer ID。临时签名能证明的只有「加固运行时加这一项授权能跑」，苹果的公证服务接不接受要等 G1.12 的开发者账号。
- **Windows 的打包未测。**

## 3. 窗口到宿主的本机 WebSocket

### 怎么测的

打包后的应用（页面地址 `tauri://localhost`，不是开发服务器），开着 CSP：`connect-src 'self' ipc: http://ipc.localhost ws://127.0.0.1:*`。宿主监听 `127.0.0.1` 上系统分配的端口；令牌由 Rust 用 `/dev/urandom` 生成，经标准输入交给宿主，窗口用 `invoke` 向 Rust 要。

### 结果（macOS 27.2，WKWebView）

| 项目 | 结果 |
|---|---|
| 页面是不是安全上下文 | 是 |
| 从 `tauri://localhost` 连 `ws://127.0.0.1` | **通，没有被当成混合内容拦掉** |
| 建立连接 | 13–21 ms |
| 一问一答 300 次 | 中位数不到 1 ms，最慢 6 ms（页面的计时精度是 1 ms） |
| 来回 1 MB 的文本 | 4–6 ms，内容完整 |
| 来回 256 KB 的二进制 | 1 ms |
| 宿主连发 20000 条 200 字节的消息 | 0.3 秒收完，每秒约 6.5 万条 |
| 令牌不对 | 连接被宿主关掉（关闭码 4401） |
| 宿主看到的 `Origin` 请求头 | `tauri://localhost`，可以在令牌之外再核对一次来源 |

### `invoke` 长轮询（后备通道）

| 项目 | 结果 |
|---|---|
| 一个窗口里挂着 1、4、6、8、16、32、64 个没返回的长轮询时，别的 `invoke` | 不受影响：中位数 1 ms，最慢 2 ms |
| 8 个窗口各自长轮询，Rust 在 1.2 秒里推 200 个事件 | 每个窗口都收全 200 个，延迟中位数 1 ms，最慢 4 ms |

担心过的「自定义协议的并发请求有上限」在 64 个以内没有出现。

### 结论：成立

- macOS 上直接用 WebSocket，方案里的后备（经 Rust 中转）在 macOS 27.2 上用不上。
- 后备通道本身可行，留着给两种情况：macOS 15 上如果不通；Windows 上如果不通。这两处都没测。

## 4. 自定义协议上的 `import()` 和共用 React

### 怎么测的

Rust 注册 `plugin` 协议，从资源目录里读文件，回 `Access-Control-Allow-Origin` 和按扩展名定的 MIME，文件不存在回 404。演示插件用 esbuild 打包，`react` 和 `react/jsx-runtime` 改写成指向两个转接模块；转接模块只把页面里已经加载的那份 React 再导出一遍。

### 结果（macOS 27.2）

| 项目 | 结果 |
|---|---|
| `import('plugin://localhost/demo/island.js')` | 通，1–3 ms |
| 插件拿到的 React 是不是页面的那一份 | 是 |
| 插件组件用 `useState`，渲染后点一下 | 正常（`clicks 0` 变成 `clicks 1`） |
| 模块里的相对导入、`import.meta.url` | 正常 |
| 用 `<link>` 加载样式 | 生效 |
| `fetch` 协议上的 JSON | 正常 |
| 同一个地址再 `import` 一次 | 拿到同一个模块 |
| 地址后面加 `?v=2` | 拿到新的模块 |
| 不回 CORS 头 | 加载被拒：`Cross-origin script load denied by Cross-Origin Resource Sharing policy.` |
| MIME 回成 `text/html` | 加载被拒，报错里写明了 MIME 和地址 |
| 文件不存在（404） | 加载失败，报错只有一句 `Importing a module script failed.`，看不出原因 |

### 结论：成立

两条实现时要照做的：

- **转接模块用相对路径引用**（`../__shared/react.js`），不用绝对地址。同一个协议在 macOS 上是 `plugin://localhost/…`，在 Windows 上是 `http://plugin.localhost/…`，写绝对地址的话同一个插件包没法两边通用。
- 404 的报错没有信息量，窗口里的加载器要在 `import()` 之前自己先确认文件在不在，才能给出「哪个插件的哪个文件没找到」。

没测的：开发者工具里 source map 是否生效、样式里引用的字体、Windows。

## 5. 宿主崩溃、卡死后的重启和窗口重连

### 怎么测的

Rust 每 250 ms 看一次宿主进程还在不在，并经标准输入发一次心跳；2 秒没有回应算卡死，杀掉重启。每次重启换新的端口和令牌。窗口发现连接断了，就反复用 `invoke` 问 Rust 要新的地址，连上后取一份当前状态。

### 结果

| 情况 | Rust 发现 | 新宿主就绪 | 窗口重新连上并拿到状态 |
|---|---|---|---|
| 杀掉宿主（`SIGKILL`），Node，6 次 | 135–245 ms | 再过 61–83 ms | 杀掉后 231–353 ms |
| 杀掉宿主，Bun，3 次 | 97–251 ms | 再过 28–93 ms | 264–459 ms |
| 宿主死循环 | 约 1.9 秒（心跳超时设的 2 秒） | 再过 52–61 ms | 约 2.0 秒 |
| 应用自己被 `kill -9` | — | — | 宿主 1.5 秒内自己退出，不留孤儿进程 |

- 发现的时间主要是轮询间隔和心跳超时，都是可调的参数。
- 每次重启后进程号、端口、令牌都是新的；窗口不用重载。
- 宿主内存里的状态确实丢了（测试里的计数回到初始值）。方案里「插件的状态不能只放在内存里」是必须的。
- 应用被强杀时宿主跟着退出，靠的是宿主发现标准输入关了就退出，不依赖进程组。

### 结论：成立

没测的：重启那一刻正在进行的调用怎么收场、多个窗口同时重连、Windows 上的作业对象。

## 6. 窗口全隐藏时的定时器、睡眠唤醒

### 怎么测的

应用启动时主窗口就不显示，另外再开一个从不显示的窗口，所以应用没有任何可见的窗口。宿主里一个 100 ms 的 `setInterval`，每 10 秒记一次这段时间里跑了多少次、最晚的一次晚了多少。跑了两轮，每轮 8 分钟。期间电脑在正常使用（有别的程序在前台），没有睡眠。

### 结果（Node 宿主）

| | 第一轮 | 第二轮 |
|---|---|---|
| 每 10 秒跑的次数（应当是 100） | 99–100 | 99–100 |
| 最晚的一次 | 34.8 ms | 37.8 ms |
| 平均晚多少（每 10 秒一段里最大的） | 1.7 ms | 1.8 ms |

47 个 10 秒的时间段里没有一段少于 99 次。宿主是普通的子进程，应用的窗口全隐藏对它没有影响。

### 结论：成立；睡眠唤醒未测

- 8 分钟不能代表几小时：系统对长时间在后台的进程有没有进一步的节能调度，这里看不出来，留给第 1 阶段的 8 小时长跑。
- **睡眠唤醒没测。** 要测的话：在终端里跑下面这条（应用没有窗口，20 分钟后自己退出），合上盖子几分钟再打开，然后看 `runs/sleep/timers-host.jsonl`：唤醒后应当有一行的「最晚」等于睡了多久，之后恢复到每 10 秒 99–100 次。

```bash
cd ~/Desktop/projects/fuyu-v3-spike && mkdir -p runs/sleep && SPIKE_OUT=$PWD/runs/sleep SPIKE_SCENARIO=timers SPIKE_DURATION=1200 app/src-tauri/target/release/bundle/macos/FuyuV3Spike.app/Contents/MacOS/fuyu-v3-spike
```

## 7. 对照：隐藏 WebView 当宿主

和第 6 项同一次运行：那个从不显示的窗口里跑 Cordis 的内核（浏览器里能直接用，只是没有加载器）和同样的 100 ms 定时器。两轮的区别是这个窗口的 `backgroundThrottling`。

| | 默认 | 设成 `disabled` |
|---|---|---|
| 页面脚本能不能跑起来 | 能，内核和两个插件都起来了 | 能 |
| 8 分钟里 100 ms 的定时器 | **一次汇报都没有**：定时器实际上没在跑 | 每 10 秒跑 10–11 次，也就是**每秒 1 次**，每次晚约 900 ms |
| 8 分钟里有没有被整页挂起 | 看不出来（定时器本来就不跑） | 没有，一直到结束都在跑 |
| 比不带宿主多占的内存 | 13.8 MB | 14.2 MB |
| 对安装包的影响 | 没有 | 没有 |

同一时间里 Node 宿主的定时器最晚 38 ms。

### 结论：不改现在的决定

- 隐藏 WebView 在内存（少约 8 MB）和安装包（不增加）上都更好，但它里面的定时器最多每秒 1 次，不设那个开关时干脆不跑。调研里引用的第三方测量（关掉挂起后约 1 Hz）在这台机器上复现了。
- 加上 Cordis 的加载器和热重载只能在 Node 里跑、插件不能用 Node 的接口和 npm 包，决定 4（独立的 Node 进程）的理由都还在。
- 它是安装包这个代价唯一能完全避开的路。如果最后觉得多 44 MB 不能接受，这是回头要重新评估的那个方案，代价是定时全部交给 Rust、加载器自己写、插件不能用 npm。

## 8. rutis 小样

读的是 rutis 的提交 `1dd73888`（main，v0.21.0 之后 129 个提交）。小样由一个子代理做，下面的数字我抽查过它留下的日志和源码行数。

**跑通了，也嵌进了 Tauri 2。** Rust 里标一个 `Greeter` 服务，Node 里的 TypeScript 插件调用它；同一套代码嵌进最小的 Tauri 程序，页面 `invoke` → Rust → rutis → TS 插件 → 原路返回。只在这台 Mac 上跑过，没打包。

### 「标记即服务」是怎么做的

| 部分 | 行数（不含测试） | 做什么 |
|---|---|---|
| 属性过程宏 `#[rutis::service]` | 1042 | 标在 `impl` 块上，生成一个按方法名分发的 `match` 和一条登记 |
| 登记表和支撑代码 | 1505 | 程序加载时自动登记（往各平台的初始化段放函数指针，和 `inventory` 同一个原理） |
| 按名字对外提供 | 881 | 把登记的条目挂成能跨进程按名字调用的服务 |
| TypeScript 类型生成 | 3758 | 构建时用 `syn` **读源码文本**推出类型，自己实现了一遍 serde 的属性 |

和方案里的说法不一样的地方：

- 标的是 `impl` 块，而且只能是 `&self` 的方法，**不能标自由函数**。浮屿的 Tauri 命令都是自由函数。
- TypeScript 类型不是标记生成的，是另一个 crate 在 `build.rs` 里生成的；标记本身不产生参数的描述，只有方法名。

### 自己照着做要多少

子代理写了一个最小版并跑通：属性宏 129 行、运行时 176 行，共 305 行。标在自由函数上（同步或 `async`），生成 JSON-RPC 的分发入口，用 `ts-rs` 导出 TypeScript 声明。依赖 `syn`、`quote`、`inventory`、`ts-rs`。

它还缺：错误类型的声明、注入状态的参数（对应 Tauri 的 `State`、`AppHandle`）、重名检查、测试；和 `#[tauri::command]` 叠在同一个函数上没试过。补齐估计 600–900 行，这是估计，不是实测。

### 进程恢复

| 问题 | 实测 |
|---|---|
| Node 被杀后多久发现 | 几十毫秒内（通道断开就知道，没有轮询） |
| Rust 一侧正在等的调用 | 立刻以明确的错误结束（`peer-gone`，带是哪个插件的哪个方法），不挂着 |
| 恢复前新发起的调用 | 立刻失败，不排队、不重试 |
| 自动重启 | 库本身不重启；接上它提供的重启循环后约 1.25 秒恢复（其中 1 秒是写死的等待），自己立刻重启约 0.26 秒 |
| JS 进程里的状态 | 丢失，插件的 `apply` 重跑 |
| JS 调 Rust 的 `async` 方法执行到一半 | **被取消**，停在某个 `await` 上不再继续。文档里没写 |
| Node 卡死（`SIGSTOP`） | **发现不了**：本地管道上没有心跳，状态一直显示就绪 |

### 结论

- 「标记即服务」值得照着做，而且比 rutis 的实现简单得多：TypeScript 类型交给 `ts-rs` 的派生宏，不用读源码那 3700 多行。第 3 阶段再写。
- 进程恢复上我们第 5 项的做法（心跳加超时）比 rutis 多管了卡死这一种情况，保留。可以学它的一点：**通道一断，等待中的调用立刻带着原因失败**，不等超时。
- 它一个月发了 23 个版本、最近 5 个里有 4 个标了不兼容改动，嵌入还会让可执行文件多 9.6 MB。决定 13（不依赖它）不用改。

没测的：Windows、打包、它发布到 crates.io 和 npm 上的版本（用的是同一个提交的源码）、Bun 运行时。

## 要你定的

1. **继续、改方案，还是停。** 建议继续：Mac 上前 3 项都成立，要改的都是上表里的细节。风险是 Windows 一项没测，建议第 1 阶段开工的同时，在 Windows 那台机器上把第 2、3、4 项补测掉（临时项目拷过去，Rust 一侧有两处只写了 Unix 的做法要先改，见任务文件的备注），有不通的再回头改。
2. **Node 还是 Bun。** 建议 Node，理由见第 1 项的结论。
3. **安装包变大能不能接受。** Mac 的 dmg 从 13 MB 到约 57 MB，更新包每次多约 42 MB。建议接受，并做下面表里的前两项。

### 安装包能怎么小

用户后来定的是下表第 4 行的变体：先用用户电脑上的 Node，没有才下载（见「报告之后定的」）。「不能用用户自己装的 Node」是当时的建议，没有被采纳。

宿主不是可选件（内置功能都是插件，没有它岛屿只剩空壳），也不能用用户自己装的 Node（多数人没装、版本不可控、从 `PATH` 里找可执行文件来跑同权的代码不安全）。能选的是这些：

| 做法 | 效果 | 代价 | 测过吗 |
|---|---|---|---|
| dmg 改 LZMA 压缩 | 省约 13 MB，更新包不受益 | 打包参数要改 | 测了 |
| 去掉 Node 的调试符号 | 省约 5 MB | 宿主崩溃时的原生调用栈没有符号 | 测了，能跑 |
| Node 放在应用包之外，按版本存一份，版本变了才重下 | 日常更新回到十几 MB；安装包不变 | 多一套检查、下载、校验 Node 的逻辑 | 没测 |
| 首次启动时再下载 Node | 安装包保持 13 MB | 第一次启动要联网下 30–40 MB，下完之前内置功能不可用；离线装不了；要自己放镜像 | 没测 |
| 自己编一个精简的 Node | 估计能小三分之一 | 每次 Node 出安全更新，两个系统都要重编 | 没测 |
| 换成 Bun | 只小 3 MB | 见第 1 项 | 测了 |
| 回到隐藏 WebView 当宿主 | 不增加 | 见第 7 项 | 测了 |

## 报告之后定的（2026-11-14）

用户看过上面的结果后定了：**宿主用 Node；安装包不带 Node，首次启动时先看用户电脑上有没有装、能不能用，没有或不能用才下载**（方案的决定 16）。这样第 2 项里「把 Node 打进包里」的签名和授权不再需要，安装包也不变大。

为这个决定补测了三样（macOS 27.2，同一个临时应用，不带 Node 打包，应用本身 11.1 MB）：

| 用哪个 Node | 结果 |
|---|---|
| 本机 Homebrew 装的 Node 26.12.0（临时签名，没开加固运行时） | 全部自动测试通过 |
| 下载的官方 Node 26.13.1，原样不重新签名（Node.js 基金会的签名） | 全部自动测试通过；应用自己开着加固运行时，不影响子进程 |
| 不指定路径，让应用从 `PATH` 里找 `node`（从终端启动） | 找到了 Homebrew 的那个，全部通过 |

要留意的：

- 新打的包第一次拉起宿主花了 **25 秒**，第二次 172 ms。和第 1 项里「第一次运行慢」是同一类现象，这次更久，原因没查清。首次启动的体验要把它算进去。
- **从访达启动时应用拿到的 `PATH` 没测到**：想用 `open` 模拟，结果它把终端的环境一起带过去了。图形界面的应用通常拿不到 Homebrew 和版本管理器加的路径，所以不能只靠 `PATH` 找，要去常见的安装位置找。
- 没测的：22、24 这些更旧的 Node；nvm / fnm / volta 装的 Node；下载、校验、放进数据目录这一套流程本身；Windows。

临时项目跟着改了三处，让它不只在 Unix 上能编译：令牌读不到 `/dev/urandom` 时换一种取法；运行时先找应用旁边的，没有就用 `PATH` 里的；加了一份不带附带程序的打包配置。源码（不含依赖和构建产物）打成了 `fuyu-v3-spike-src.zip`，给 Windows 上补测用。

## 过程里碰到的

- 临时项目要放一份和浮屿相同的 `rust-toolchain.toml`（1.99.1）。用本机默认的 1.95 时，`tauri build` 编出来的过程宏动态库加载不了（`mis-aligned LINKEDIT string pool`），原因没有查清。
