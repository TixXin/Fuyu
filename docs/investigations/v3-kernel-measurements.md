# 插件平台第 3 版：内核的实测（第 1 阶段第 9 步）

E36.1（#291）第 9 步的测量：宿主进程本身的内存、启动时间、被杀后恢复的时间和长跑（按用户要求跑了 1 小时），以及整个岛屿开着第 3 版时的内存和冷启动（[进度](../architecture/plugins/v3-progress.md)「基线和实测」里「第 1 阶段后」那一列的数从这里来）。

保证清单和它的测试见 [v3-guarantees.md](../architecture/plugins/v3-guarantees.md)。

## 结论

- **整个岛屿**：开着第 3 版（`FUYU_PLUGINS_V3=1`，没有插件）比关着多一个 Node 宿主进程，`phys_footprint` 一直是 24.8–25.1 MB，其余进程没有多出东西；在 40 MB 的验收线以内。三次交替测量的差是 −6、+13、+17 MB，被 WebKit 自己的起伏（同一种设置两次之间差 50 MB 以上）盖住了，所以按宿主进程本身算多 25 MB。冷启动开着和关着一样（690 对 679 ms），都比基线的约 0.8 秒快；岛屿不等宿主就绪，这和方案的设计一致。
- 宿主自己约 28 MB，离方案的验收线（整个岛屿比基线多不超过 40 MB）有十来 MB 的余量，空插件几乎不占内存。真插件的代价要等第 3 阶段内置功能变成插件后再量。
- **发现一处可以改的**：Rust 的看管（`src-tauri/crates/plugin-base/src/supervisor.rs` 的 `watch`）每过 `ping_every`（默认 1 秒）才看一次宿主退出没有，所以宿主崩溃后要 0–1 秒才被发现，平均多等约 0.5 秒。第 0 阶段的临时代码每 250 ms 查一次，恢复约 0.3 秒。建议：宿主的标准输出读到 EOF（管道那头没了）时唤醒看管线程（`Inner::wake`），这样崩溃后几毫秒就能发现，恢复时间回到约 0.16 秒；卡死仍然靠心跳。这只是看管的参数，不影响正确性。已在 #347 改好（读到 EOF 就唤醒看管），上面「按 1 秒间隔」那一行是改之前的情况。

## 怎么测的

脚本是 [`scripts/plugins-v3/measure-host.mjs`](../../scripts/plugins-v3/measure-host.mjs)（读内存在 `measure-memory.mjs`，测试在 `tests/scripts/plugins-v3-measure.test.mjs`）。它不经过 Rust，直接用 Node 拉起宿主，和 Rust 拉起时的参数一样：`node --disallow-code-generation-from-strings packages/plugin-base/src/host/main.mjs --dir <临时目录>`，经标准输入输出说 JSON-RPC。

- **空插件**：每个插件是一个文件 `export const name = "empty-<i>"; export function apply() {}`，写进临时目录的 `plugins/`，`plugins.yml` 里一个插件一项。
- **内存**：macOS 读宿主那一个进程的 `phys_footprint`（`/usr/bin/footprint -f bytes --noCategories -p <pid>`，和第 0 阶段用 `proc_pid_rusage` 读的是同一个数，也是活动监视器「内存」一栏的数）。Windows 读私有内存（PowerShell 的 `(Get-Process -Id <pid>).PrivateMemorySize64`）。宿主没有子进程，所以只读它一个。
- **启动**（`startup`）：从 `spawn` 到收到 `ready` 通知的时间。`ready` 在内核和配置里的插件都加载完、窗口的 WebSocket 开好之后才发，脚本还核对 `ready` 里 N 个插件都是 `running`。`ready` 之后等 6 秒（和第 0 阶段「启动 6 秒后读」一样），每秒读一次内存、读 5 次取中位数，然后关掉标准输入让宿主退出。N = 0、10、50 各来 5 轮，表里是 5 轮的中位数。
- **重启**（`restart`）：宿主就绪后 0.5 秒，用 `SIGKILL` 杀掉（Windows 上 Node 的 `kill` 是 `TerminateProcess`），模拟 Rust 看管：发现退出后立刻拉起新宿主（Rust 第一次重启不等待），量从杀掉到新宿主 `ready`。「发现」有两种：`--poll 0` 是一退出就发现；`--poll 1000` 照 Rust 现在的做法每 1 秒查一次，10 轮的检查时刻在 1 秒里均匀错开（第 i 轮在杀掉后 (i + 0.5) × 100 ms 第一次查），所以中位数约等于平均情况。10 个空插件，10 轮。
- **长跑**（`soak`）：拉起带 N 个插件的宿主，每隔 `--every` 秒先发一次 `ping`（记下往返时间），再读一次内存，写一行 CSV：`at,elapsed_s,memory_mb,ping_ms,host_pid,restarts`。`--churn S` 时宿主带 `--watch` 启动，脚本每 S 秒改写 `plugins.yml`，把第一个插件停用或启用，模拟一直有插件在装卸。宿主中途退出时脚本重新拉起并把 `restarts` 加 1（正常情况下一直是 0）。

## 结果（macOS）

### 宿主的内存和启动

原始数据：

| 空插件 | 拉起到 `ready`（5 轮，ms） | 中位数 | 内存（5 轮，MB） | 中位数 |
|---|---|---|---|---|
| 0 | 138、146、151、146、146 | 146 ms | 27.6、27.4、27.7、27.8、27.6 | 27.6 MB |
| 10 | 150、165、145、135、161 | 150 ms | 29.3、29.0、29.3、29.3、29.1 | 29.3 MB |
| 50 | 148、151、155、161、145 | 151 ms | 32.8、32.6、32.8、33.1、32.8 | 32.8 MB |

和第 0 阶段的对照（同一台机器，单独跑宿主，启动 6 秒后读）：

| 第 0 阶段 | 内存 | 这次 | 内存 |
|---|---|---|---|
| 内核、加载器、两个插件 | 23.5 MB | — | — |
| 再加热重载和 WebSocket 服务 | 28.3 MB | 宿主（加载器、WebSocket 服务、JSON-RPC，不开热重载），0 个插件 | 27.6 MB |
| 打成单个文件、放进 Tauri 应用的宿主 | 21.9–22.6 MB | （第 1 阶段还没打包，宿主从源码目录加载） | |

| 第 0 阶段 | 时间 | 这次 | 时间 |
|---|---|---|---|
| 进程启动到两个插件都跑起来 | 84 ms | 进程启动到 `ready`（10 个插件） | 150 ms |

- 内存和第 0 阶段同样配置的数基本一样。正式版的宿主会打成一个文件（方案：约 215 KB）；第 0 阶段放进应用的单文件宿主是 22 MB，但那个配置不同（只有心跳、没有加载器的配置文件），能不能少这么多，打包后再量。
- 启动比第 0 阶段多约 65 ms：这次量到的是 `ready`，中间还有开 WebSocket 服务、`settle` 等全部插件，加载也是从源码目录逐个解析 `vendor/cordis` 的几个包（推断这是多出来的主要部分，没有拆开量）；第 0 阶段量的是两个插件跑起来那一刻。0 和 50 个插件差不到 10 ms，时间都花在宿主自己身上。打成单个文件后应该会少一截，到时候再量。岛屿不等宿主就绪（方案「启动和性能」），这个数不进冷启动。

### 杀掉后恢复

| 发现退出的方式 | 10 轮的总时间（ms） | 中位数 |
|---|---|---|
| 一退出就发现（`--poll 0`） | 142、162、145、149、146、163、167、154、195、167 | 158 ms |
| 每 1 秒查一次（`--poll 1000`，Rust 现在的做法） | 185、317、411、508、604、717、839、960、1013、1083 | 661 ms |

- 进程被杀到 Node 报告它退出只要 2–8 ms，新宿主从拉起到 `ready` 133–208 ms，其余全是等下一次检查。
- 第 0 阶段（每 250 ms 查一次）是杀掉后 231–353 ms 窗口重新连上。这里没有窗口重连那一段（第 0 阶段量的是约 100 ms），窗口那一侧要等第 6 步接上后在真岛上量。

### 长跑（10 分钟短跑）

命令：

## 整个岛屿的内存和冷启动（macOS）

测法和 [进度](../architecture/plugins/v3-progress.md)「基线和实测」里 macOS 的基线一样，只多了开关这一项：

- 构建：`CARGO_PROFILE_DEV_OPT_LEVEL=3 CARGO_PROFILE_DEV_DEBUG=0 CARGO_TARGET_DIR=src-tauri/target/agents pnpm tauri build --debug --no-bundle`，代码是 `main` 的 `4170b870`。和 Windows 一样，这个目录相对 `src-tauri` 解析，产物在 `src-tauri/src-tauri/target/agents/debug/fuyu`（基线那次的记录写的是 `src-tauri/target/agents`）。同一个可执行文件量两种设置：开关只看环境变量，开发构建（`debug_assertions`）里设 `FUYU_PLUGINS_V3=1` 才拉起宿主。
- 身份：`FOCUSD_DEV_LANE=36`，数据是基线那次复制的副本。开着时宿主用这台电脑上的 Node 26.12.0（`/opt/homebrew/bin/node`），`plugins-v3/plugins.yml` 是 `[]`，也就是没有插件；每次启动的日志里都有 `[plugins-v3] host ready`。
- 冷启动：临时项目的 `tools/launch-time` 拉起进程，到屏幕上出现这个进程的第一个窗口（每 2 ms 查一次）。每次看到窗口 3 秒后结束进程，隔 8 秒再启动。关、开交替，各 5 次。
- 内存：`tools/mem.py <pid> 20 180`，岛屿进程加上记在它名下的全部进程（WebKit 的辅助进程、媒体适配脚本、音频辅助进程，开着时还有 Node 宿主）的 `phys_footprint` 之和，启动 20 秒后每 10 秒读一次、读 180 秒，取中位数。关、开交替，各 3 次。
- 当时在跑的：做测量的 Claude Code 会话（岛上显示它的状态）、下面的长跑（宿主一个进程，CPU 很小），用户的 `pnpm tauri dev` 也开着。日期 2026-11-15。新编出来的可执行文件第一次启动用了 4.5 秒（`tccd` 这次没有卡几分钟），这一次不计。

- **内存**：开着时多的是 Node 宿主一个进程，三次都是 24.8–25.1 MB；岛屿的 Rust 主进程（107–121 MB）、WebKit 的 GPU 进程（18–23 MB）和 7 个网页进程（合计 315–373 MB）开关两边没有可分的差别，网页进程的个数也一样。合计的差（中位数差 17 MB，三对分别 −6、+13、+17 MB）比宿主还小，是因为 WebKit 自己起伏很大：同一种设置两次之间就差 50–60 MB，一次读数里会冒出几十 MB 的尖峰（主网页进程 80–145 MB 之间跳，偶尔多一个 `MTLCompilerService`）。所以结论按宿主进程算：**多 25 MB，验收线 40 MB 以内**。插件真跑起来后宿主会再涨，见上面每个空插件约 0.1 MB、一直装卸时最多到 45 MB。
- **冷启动**：开着和关着一样，都比基线快（基线 763–978 ms）。岛屿拉起宿主不等它就绪，宿主就绪是窗口出来之后的事。
- 关着的合计（476.5 MB）和基线（约 490 MB）在同一个范围里。基线记录里 Rust 主进程是 32–40 MB，这次是 107–121 MB，两次都是关着第 3 版，差别不来自第 3 版（可能是这之间合入的别的改动，或者两次的拆法不同），没有查。
- **作废的一轮**：第一轮（不交替，先 5 次关、再 5 次开）里，关着的第 2 次内存在启动 60 秒后从 480 涨到 650–725 MB，多出一个网页进程、一个 Safari 辅助进程和 `MTLCompilerService`；那时另一个会话正好用同一个 lane 36 起了一次开发版，被单实例挡下（单实例会把已经在跑的岛屿叫出来），开着的前两次启动时它还往这个数据目录装过一个演示插件。所以第一轮整轮不用（数字：冷启动关 693–1104 ms、开 689–1246 ms，内存关 487 / 652 MB、开 623 / 550 MB），表里是第二轮。之后量这个，要确认没有别的会话用同一个 lane。

## 长跑

方案的验收线是「连跑 8 小时不持续增长」。**这次按用户要求（2026-11-15）只跑了 1 小时，不是方案写的 8 小时。**

### 怎么跑

```bash
caffeinate -i node scripts/plugins-v3/measure-host.mjs soak --plugins 10 --busy 1 --minutes 480 --every 60 --out host-soak-8h.csv
```

```bash
node scripts/plugins-v3/measure-trend.mjs host-soak-8h.csv
```

- `--busy N` 再加 N 个「干活的」插件，比全是空插件更接近真插件：每个用受管定时器 `ctx.setInterval` 每秒做一次事——造 2000 个对象、JSON 来回转一遍、`ctx.emit` 一个事件（自己用 `ctx.on` 收下，只留最近 60 个），再用 `ctx.setTimeout` 隔 10 ms 把计数写进工作目录的文件。脚本结束时读这个文件，确认插件一直在跑（`busyTicks`）。
- 每分钟一行 CSV，8 小时约 480 行；CSV 不进仓库，结论和关键数字写到这一页。电脑不要睡眠（macOS 用 `caffeinate -i` 包着；Windows 把电源计划的睡眠关掉），否则读数会断开。
- `measure-trend.mjs` 去掉前 10 分钟（`--skip`，V8 的新生代在分配多时会先涨到上限再稳住，见保证清单第 18 条的说明），对剩下的读数做线性拟合，给出每小时涨多少 MB（`slopeMBPerHour`），以及第一个小时和最后一个小时的中位数、最高 `ping`、重启次数。斜率接近 0、头尾两个小时的中位数差不多、`restarts` 一直是 0、`ping_ms` 一直是个位数就算通过。
- 想看反复装卸，再跑一次加 `--churn 5`（8 小时约 5700 次装卸）。
- 这量的是宿主进程本身。整个岛屿开着第 3 版时多的就是这个进程（见上面「整个岛屿」）。

### 结果（macOS）

2026-11-15 06:25–07:26（UTC），10 个空插件加 1 个干活的插件，`--every 60`；原定 480 分钟，用户改成 1 小时后在 3600 秒那一行之后停掉（脚本和宿主一起结束，没有留下进程）。

- **没有重启**：61 行读数，宿主一直是同一个进程，`restarts` 0，`ping` 0–6 ms（只有一次 6 ms，其余 0–2 ms）。干活的插件 1 小时里跑了 3614 次，每秒一次，一次没断。
- **内存是锯齿**（MB，每 10 分钟的中位数 / 最低–最高）：

  | 分钟 | 0–9 | 10–19 | 20–29 | 30–39 | 40–49 | 50–60 |
  |---|---|---|---|---|---|---|
  | 内存 | 27.5 / 26.5–29.6 | 30.4 / 28.8–32.0 | 33.3 / 32.2–34.3 | 35.3 / 34.7–37.0 | 31.7 / 30.9–36.4 | 33.9 / 32.9–35.5 |

  从开头的 26.5 MB 每分钟涨约 0.2 MB，第 39 分钟到 37.0 MB，第 41 分钟一次回收掉到 31.1 MB，之后又按同样的速度涨，到第 60 分钟是 35.5 MB。这是干活的插件每秒造的对象慢慢升进 V8 老生代、攒到一定量做一次完整回收的样子，和前面「一直装卸」的对照一样有上限。
- `measure-trend.mjs` 拟合出的斜率是每小时 3.97 MB，但 1 小时里只有一个锯齿，这个斜率主要是锯齿的上坡，不能当成增长速度。比较能说明问题的是回收后的谷底：开头 26.5 MB（刚启动、还没预热），回收后 31.1 MB，多出的 4.6 MB 里有多少是预热、有多少是真在涨，要看下一个锯齿的谷底，1 小时分不出来。
- **结论**：1 小时内没有看到持续增长的迹象（有回收、有上限、没有重启），但 1 小时只够看到一个回收周期，「8 小时不持续增长」这条验收线这次没有验证。要验证就照上面的命令跑满 480 分钟，看几个谷底是不是持平。

## 没测的

- Windows 上全部（见上面）。
- 8 小时长跑：按用户要求只跑了 1 小时，见上面「长跑」。
- 整个岛屿装了真插件时的内存，和整个岛屿的长跑：这次的岛屿没有插件，长跑只跑了宿主。
- 真插件的内存：空插件几乎不占内存，真插件的代价要等内置功能变成插件。
- 宿主卡死后的恢复：Rust 看管的心跳超时是 2 秒，恢复时间约等于它，第 0 阶段已经量过（约 2 秒），这次的脚本只模拟崩溃。
- 打成单个文件的宿主：第 1 阶段还没打包。
