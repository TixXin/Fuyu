# 插件平台第 3 版：内核的实测（第 1 阶段第 9 步）

E36.1（#291）第 9 步里不依赖窗口的那部分：宿主进程本身的内存、启动时间、被杀后恢复的时间，以及长跑的脚本。整个岛屿的内存和冷启动（[进度](../architecture/plugins/v3-progress.md)「基线和实测」里「第 1 阶段后」那一列）要等窗口接上宿主后在真岛上量，不在这一页。

保证清单和它的测试见 [v3-guarantees.md](../architecture/plugins/v3-guarantees.md)。

## 结论

| 项 | macOS（这台 Mac） | Windows |
|---|---|---|
| 宿主进程内存，0 / 10 / 50 个空插件 | 27.6 / 29.3 / 32.8 MB（`phys_footprint`） | 未测 |
| 每多一个空插件 | 约 0.1 MB | 未测 |
| 拉起宿主到 `ready` | 146 / 150 / 151 ms（中位数） | 未测 |
| 杀掉宿主到新宿主 `ready`（一发现退出就重启） | 158 ms（中位数，142–195） | 未测 |
| 同上，按现在 Rust 看管的检查间隔（1 秒） | 中位数 661 ms，最长约 1.1 秒 | 未测 |
| 10 分钟短跑（10 个插件，每 5 秒停用 / 启用一个） | 27.3–30.1 MB，没有重启，`ping` 0–2 ms；闲置时一直是 29.0–29.1 MB，一直装卸时在 31–45 MB 之间起伏、会回收 | 未测 |

- 宿主自己约 28 MB，离方案的验收线（整个岛屿比基线多不超过 40 MB）有十来 MB 的余量，空插件几乎不占内存。真插件的代价要等第 3 阶段内置功能变成插件后再量。
- **发现一处可以改的**：Rust 的看管（`src-tauri/crates/plugin-base/src/supervisor.rs` 的 `watch`）每过 `ping_every`（默认 1 秒）才看一次宿主退出没有，所以宿主崩溃后要 0–1 秒才被发现，平均多等约 0.5 秒。第 0 阶段的临时代码每 250 ms 查一次，恢复约 0.3 秒。建议：宿主的标准输出读到 EOF（管道那头没了）时唤醒看管线程（`Inner::wake`），这样崩溃后几毫秒就能发现，恢复时间回到约 0.16 秒；卡死仍然靠心跳。这只是看管的参数，不影响正确性，已经告诉负责第 1 阶段的会话。

## 怎么测的

脚本是 [`scripts/plugins-v3/measure-host.mjs`](../../scripts/plugins-v3/measure-host.mjs)（读内存在 `measure-memory.mjs`，测试在 `tests/scripts/plugins-v3-measure.test.mjs`）。它不经过 Rust，直接用 Node 拉起宿主，和 Rust 拉起时的参数一样：`node --disallow-code-generation-from-strings packages/plugin-base/src/host/main.mjs --dir <临时目录>`，经标准输入输出说 JSON-RPC。

- **空插件**：每个插件是一个文件 `export const name = "empty-<i>"; export function apply() {}`，写进临时目录的 `plugins/`，`plugins.yml` 里一个插件一项。
- **内存**：macOS 读宿主那一个进程的 `phys_footprint`（`/usr/bin/footprint -f bytes --noCategories -p <pid>`，和第 0 阶段用 `proc_pid_rusage` 读的是同一个数，也是活动监视器「内存」一栏的数）。Windows 读私有内存（PowerShell 的 `(Get-Process -Id <pid>).PrivateMemorySize64`）。宿主没有子进程，所以只读它一个。
- **启动**（`startup`）：从 `spawn` 到收到 `ready` 通知的时间。`ready` 在内核和配置里的插件都加载完、窗口的 WebSocket 开好之后才发，脚本还核对 `ready` 里 N 个插件都是 `running`。`ready` 之后等 6 秒（和第 0 阶段「启动 6 秒后读」一样），每秒读一次内存、读 5 次取中位数，然后关掉标准输入让宿主退出。N = 0、10、50 各来 5 轮，表里是 5 轮的中位数。
- **重启**（`restart`）：宿主就绪后 0.5 秒，用 `SIGKILL` 杀掉（Windows 上 Node 的 `kill` 是 `TerminateProcess`），模拟 Rust 看管：发现退出后立刻拉起新宿主（Rust 第一次重启不等待），量从杀掉到新宿主 `ready`。「发现」有两种：`--poll 0` 是一退出就发现；`--poll 1000` 照 Rust 现在的做法每 1 秒查一次，10 轮的检查时刻在 1 秒里均匀错开（第 i 轮在杀掉后 (i + 0.5) × 100 ms 第一次查），所以中位数约等于平均情况。10 个空插件，10 轮。
- **长跑**（`soak`）：拉起带 N 个插件的宿主，每隔 `--every` 秒先发一次 `ping`（记下往返时间），再读一次内存，写一行 CSV：`at,elapsed_s,memory_mb,ping_ms,host_pid,restarts`。`--churn S` 时宿主带 `--watch` 启动，脚本每 S 秒改写 `plugins.yml`，把第一个插件停用或启用，模拟一直有插件在装卸。宿主中途退出时脚本重新拉起并把 `restarts` 加 1（正常情况下一直是 0）。

## 结果（macOS）

### 宿主的内存和启动

原始数据：

| 空插件 | 拉起到 `ready`（5 轮，ms） | 中位数 | 内存（5 轮，MB） | 中位数 |
|---|---|---|---|---|
| 0 | 138、146、151、146、146 | 146 ms | 27.6、27.4、27.7、27.8、27.6 | 27.6 MB |
| 10 | 150、165、145、135、161 | 150 ms | 29.3、29.0、29.3、29.3、29.1 | 29.3 MB |
| 50 | 148、151、155、161、145 | 151 ms | 32.8、32.6、32.8、33.1、32.8 | 32.8 MB |

和第 0 阶段的对照（同一台机器，单独跑宿主，启动 6 秒后读）：

| 第 0 阶段 | 内存 | 这次 | 内存 |
|---|---|---|---|
| 内核、加载器、两个插件 | 23.5 MB | — | — |
| 再加热重载和 WebSocket 服务 | 28.3 MB | 宿主（加载器、WebSocket 服务、JSON-RPC，不开热重载），0 个插件 | 27.6 MB |
| 打成单个文件、放进 Tauri 应用的宿主 | 21.9–22.6 MB | （第 1 阶段还没打包，宿主从源码目录加载） | |

| 第 0 阶段 | 时间 | 这次 | 时间 |
|---|---|---|---|
| 进程启动到两个插件都跑起来 | 84 ms | 进程启动到 `ready`（10 个插件） | 150 ms |

- 内存和第 0 阶段同样配置的数基本一样。正式版的宿主会打成一个文件（方案：约 215 KB）；第 0 阶段放进应用的单文件宿主是 22 MB，但那个配置不同（只有心跳、没有加载器的配置文件），能不能少这么多，打包后再量。
- 启动比第 0 阶段多约 65 ms：这次量到的是 `ready`，中间还有开 WebSocket 服务、`settle` 等全部插件，加载也是从源码目录逐个解析 `vendor/cordis` 的几个包（推断这是多出来的主要部分，没有拆开量）；第 0 阶段量的是两个插件跑起来那一刻。0 和 50 个插件差不到 10 ms，时间都花在宿主自己身上。打成单个文件后应该会少一截，到时候再量。岛屿不等宿主就绪（方案「启动和性能」），这个数不进冷启动。

### 杀掉后恢复

| 发现退出的方式 | 10 轮的总时间（ms） | 中位数 |
|---|---|---|
| 一退出就发现（`--poll 0`） | 142、162、145、149、146、163、167、154、195、167 | 158 ms |
| 每 1 秒查一次（`--poll 1000`，Rust 现在的做法） | 185、317、411、508、604、717、839、960、1013、1083 | 661 ms |

- 进程被杀到 Node 报告它退出只要 2–8 ms，新宿主从拉起到 `ready` 133–208 ms，其余全是等下一次检查。
- 第 0 阶段（每 250 ms 查一次）是杀掉后 231–353 ms 窗口重新连上。这里没有窗口重连那一段（第 0 阶段量的是约 100 ms），窗口那一侧要等第 6 步接上后在真岛上量。

### 长跑（10 分钟短跑）

命令：

```bash
node scripts/plugins-v3/measure-host.mjs soak --plugins 10 --minutes 10 --every 60 --churn 5 --out soak.csv
```

结果：脚本能用，10 分钟里 10 行 CSV，宿主一直是同一个进程（`restarts` 0），`ping` 往返 0–2 ms。内存（MB，每分钟一次）：29.3、27.3、27.8、28.1、28.3、28.6、29.1、29.2、30.1、29.6。

10 分钟里内存一直往上走（约 110 次装卸，27.3 → 约 30 MB），光看这一次分不出是泄漏还是 V8 还没回收。所以又各跑了 5 分钟、每 20 秒读一次作对照：

| 秒 | 0 | 20 | 40 | 60 | 80 | 100 | 120 | 140 | 160 | 180 | 200 | 220 | 240 | 260 | 280 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 不装卸（`--churn 0`） | 29.1 | 29.1 | 29.1 | 29.1 | 29.1 | 29.1 | 29.1 | 29.0 | 29.0 | 29.0 | 29.0 | 29.0 | 29.1 | 29.1 | 29.1 |
| 每 0.5 秒装卸一次（`--churn 0.5`，约 600 次） | 29.4 | 34.5 | 35.3 | 40.1 | 43.9 | 44.9 | 45.0 | 45.3 | 30.8 | 33.6 | 31.7 | 34.1 | 34.6 | 35.6 | 33.0 |

- 闲置时宿主的内存一动不动。
- 一直装卸时内存先涨到约 45 MB，然后一次回收掉到 31 MB，之后在 31–36 MB 之间起伏：是锯齿，有上限，不是一直涨。和保证清单第 18 条看到的一样（V8 的新生代先撑大再回收）。
- 这只是几分钟的对照，「8 小时不持续增长」还是要跑下面的长跑才算数。

**未测**（这台 Mac 上做的）。在 Windows 那台机器（tixxin-computer）上的跑法：

1. 同步 `main`，`pnpm install`。
2. 在仓库根目录跑，`--node` 指向要测的 Node（不写就用当前的 `node`），两种 Node 都跑一遍：本机的 `C:\Program Files\nodejs\node.exe`，和岛屿下载的那一份（第 4b 步做完后在数据目录里）：

   ```bash
   node scripts/plugins-v3/measure-host.mjs startup --json startup.json
   ```

   ```bash
   node scripts/plugins-v3/measure-host.mjs restart --rounds 10 --poll 0 --json restart-0.json
   ```

   ```bash
   node scripts/plugins-v3/measure-host.mjs restart --rounds 10 --poll 1000 --json restart-1000.json
   ```

3. 内存读的是私有内存（每次读要起一个 PowerShell，约 0.3 秒，不影响结果）。第 0 阶段在 Windows 上单独跑宿主时私有内存比放进应用时高很多（61 MB 对 27 MB，多出的是 V8 申请了还没用的），所以这里的数要和第 0 阶段「单独跑宿主」那一组比，不要和放进应用的 27 MB 比。

## 8 小时长跑怎么跑

方案的验收线是「跑 8 小时不持续增长」。脚本已经能跑，这次只跑了 10 分钟证明能用。跑 8 小时：

```bash
node scripts/plugins-v3/measure-host.mjs soak --plugins 10 --minutes 480 --every 60 --churn 5 --out host-soak-8h.csv
```

- 每分钟一行 CSV，8 小时约 480 行；终端里同时打印每一行。CSV 不进仓库，结论和关键数字写到这一页。
- 跑两次更有用：一次 `--churn 0`（纯闲置，看宿主自己涨不涨），一次 `--churn 5`（8 小时约 5700 次装卸，对应方案的「反复加载卸载」）。
- 电脑不要睡眠（macOS 上用 `caffeinate -i` 包着跑：`caffeinate -i node scripts/plugins-v3/measure-host.mjs soak …`；Windows 上把电源计划的睡眠关掉），否则中间的读数会断开。
- 怎么看：去掉前 10 分钟（V8 的新生代在分配多时会先涨到上限再稳住，见保证清单第 18 条的说明），之后的内存做线性拟合，斜率接近 0、`restarts` 一直是 0、`ping_ms` 一直是个位数就算通过。
- 这量的是宿主进程本身。整个岛屿 8 小时的内存（验收线的另一半）要等窗口接上宿主后用真岛量，测法照 [进度](../architecture/plugins/v3-progress.md)「基线和实测」。

## 没测的

- Windows 上全部（见上面）。
- 整个岛屿的内存和冷启动：要窗口接上宿主（第 6 步之后）。
- 真插件的内存：空插件几乎不占内存，真插件的代价要等内置功能变成插件。
- 宿主卡死后的恢复：Rust 看管的心跳超时是 2 秒，恢复时间约等于它，第 0 阶段已经量过（约 2 秒），这次的脚本只模拟崩溃。
- 打成单个文件的宿主：第 1 阶段还没打包。
