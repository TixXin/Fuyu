# 展开掉帧排查记录

日期：2026-10-23。代码检查基线：`ccd845f`。

## 结论

已复现首次展开和间歇性的展开卡顿。当前最明确的瓶颈在 **WebView2 GPU 进程的栅格化与合成路径**，并非已经发现了一个耗时的 React 点击处理函数。

首次完整绘制的成本明显高于连续展开；现有宽高、圆角、阴影和滤镜动画又持续产生绘制工作。两者叠加，是目前对症状最有证据支持的解释。单独删除 `blur`，或单独跳过原生窗口同步，都不能消除首次卡顿。

闲置 25 秒后的测试也出现了较长帧间隔，但样本不足以证明某个固定闲置阈值，更不能据此认定是 WebView2 休眠、缓存回收或显卡节能。代码中未找到主动挂起 WebView2 的逻辑。

## 对应实现

### 1. 展开路径持续改变需要重绘的属性

`src/App.css`：

- `.island` 同时过渡 `width`、`height`、`border-radius`、`transform`，前四项持续 560 毫秒，还过渡背景和阴影。
- `.island__expanded` 从 `filter: blur(6px)` 过渡到 `none`；折叠内容也有 `blur(4px)` 过渡。
- 液态玻璃外层使用背景模糊，光斑使用 `blur(20px)`，同时包含多层阴影、渐变与混合效果。
- 内容通过 `inset: 0` 跟随外壳尺寸变化。改变外壳宽高时，内部也参与布局和绘制。

这不表示布局计算本身就是主要耗时；本次轨迹中更大的停顿发生在后续栅格化与合成阶段。`will-change: width, height` 也不会自动把这些动画变成只修改合成纹理的动画。

冷启动对照中，关闭滤镜仍会停顿；同时关闭阴影和滤镜后，800 毫秒内采集到的回调数从默认样式的 36–39 个提高到 92 个，但最大间隔仍有 `115.1 ms`。进一步简化尺寸动画后也仍有一次明显首次停顿。这说明需同时关注首次资源准备及持续重绘，不能把某个 CSS 属性视为已经证明的唯一根因。

### 2. 每次开合都有不必要的原生窗口操作

`src/App.tsx` 中，模式变化触发 `syncNativeInteraction`，调用 `set_island_interaction`。

`src-tauri/src/lib.rs` 中，该命令每次都：

1. 调用 `apply_stage_geometry`，设置窗口尺寸并查询显示器；即使目标位置相同，也调用 `set_position`。
2. 调用 `apply_glass_material`，清除 Acrylic，再调用 `SetWindowRgn(..., true)` 请求重绘；即使当前已经是 CSS 玻璃回退模式，也重复执行。

默认场景下原生舞台仍是 `820 × 460`，普通开合主要只需更新点击穿透所用的状态。上述重复操作可以独立优化。本次常见 IPC 耗时约 `6–23 ms`，也出现过 `67.2 ms` 的样本；但这是端到端耗时，不能直接当成渲染线程阻塞时长。绕过此命令后卡顿仍存在，因此不能只修这里就宣布解决。

### 3. 后台轮询存在额外开销，但未证明是主因

- Agent 状态每 200 毫秒查询一次；`get_agent_status` 同步访问状态及标记文件，前端每次直接 `setAgentStatus(snapshot)`。
- 音量每 500 毫秒查询一次，静音或状态不变时也可能创建新的媒体状态对象。
- 这些更新可能带动 `IslandApp` 及其内容重新渲染，值得去除无效更新。
- 媒体原生查询已使用 `spawn_blocking`。本次严重停顿没有对应 JavaScript Long Task，因此不能把轮询或媒体查询当作已经证实的主因。

## 后续优化顺序

1. **先处理渲染路径**：让展开内容尽早拥有稳定的布局尺寸，减少外壳形变期间反复栅格化；评估把动态模糊及阴影改为成本较低的进场表现，同时保留静态玻璃外观。
2. **单独验证首次绘制准备**：研究可控的启动准备或图层复用，并重新测量首次展开。仅将内容以 `opacity: 0` 挂在 DOM 中，不能假定浏览器已经完成实际绘制。
3. **避免原生重复刷新**：普通开合更新交互状态；尺寸、位置、材质确实改变时才执行相应系统调用。保留边缘收起、拖动、多屏/DPI 变化和托盘恢复所需的路径。
4. **减少轮询造成的无效渲染**：去重未改变的状态，并评估将状态文件读取移出同步命令；保持 Agent 状态响应能力。

每一项都应重新比较首次、连续和闲置后的展开，不以一次流畅采样作为验收依据。本轮是原因排查，没有修改应用代码，也未宣称修复完成。

## 第二轮：macOS（WebKit）上的展开卡顿（2026-11-21，代码阅读）

用户反馈 Mac 上面板展开仍卡。这一轮只读代码和用户的设置，没有逐帧测量。用户的设置：经典外观（不走液态玻璃和原生玻璃同步）、缩放 1、面板 800 × 360、开合动画「灵动」。

已经排除的：原生窗口改尺寸。`4e34e46d2` 之后不在侧边的岛，舞台宽度一直按展开后的宽度留，高度 `stage_height_for` 也不随形态变，开合不再调 `set_size`。

### 嫌疑（按可能性排）

1. **展开那一刻才挂载页面**。收起时 `IslandPages` 返回 `null`；只有鼠标移上岛（`useCollapsedPrewarm`，保持 1.2 秒）才提前挂上。快捷键、点消息、Agent 提醒这类不经过悬停的打开，等一帧（`deferringOpen`）后才渲染整页，React 挂载、样式、布局和第一次绘制正好落在回弹的前几帧。同一时刻 `setPanelAwake(true)` 让所有 `panelInterval` 同步各跑一次回调。WebKit 里 `@property` 变量的过渡在主线程上逐帧插值，主线程只要卡一下外壳就停一下。在 `pnpm tauri dev` 里 React 是开发模式，挂载更慢，看到的卡比正式版重。
2. **外壳每帧变形，整块面板跟着重绘**。外壳过渡宽、高、圆角，每帧都要重画外壳这块矩形。展开层淡入结束（「灵动」110ms）后不再有自己的合成层，和外壳画在同一块位图里，于是回弹剩下的约 350ms 里每帧把 800 × 360（Retina 上 1600 × 720 像素）的面板内容整体重画一遍。
3. **「灵动」的内容模糊**。展开层从 `blur(10px)` 过渡到 `none`，与外壳起步的前 110ms 重叠。模糊的是整块面板，不在合成器上做时就是逐帧软件模糊。

### 优化方向

- **A. 动画期间给展开层单独的合成层**：开合过渡进行中给 `.island__expanded` 加 `will-change: opacity`（或等效的提升），`transitionend` 后去掉，符合 motion.md「不常驻 will-change」。外壳变形只重画外壳的底色，内容层只是被裁剪。内容层的位置已经取整到整设备像素（第四轮），不会回到合成层抖动。收益预计最大、改动最小。
- **B. 别在动画里挂载和唤醒**：收起时保留最近一页的 DOM（暂停计时器，用 `content-visibility: hidden` 跳过绘制），或在开合动画结束后再 `setPanelAwake`、把各组件的立即刷新错开。代价是收起时多占一些内存，要和 macOS 内存排查（macos-memory.md）一起看。
- **C. 「灵动」的模糊减半或只在合成层上做**：和 A 一起做时模糊交给合成器；仍卡就把 10px 降到 4–6px，或换成「生长」那种 92% 放大。
- **D. 先量再改**：Safari 的 Web Inspector 连上开发版岛的 WebView，用 Timelines 录一次展开，看帧里是 Script、Layout 还是 Paint 占时间；或者在开发版里加一个只在 dev 生效的记录（每次开合的最大 rAF 间隔、长任务），比较冷打开、悬停后打开和连续打开。A–C 每一项都按这个前后对比。

### 实测（2026-11-21，开发版，MacBook 外接 4K 120Hz 主屏）

方法：开发版里 `src/windows/island/devFrameProbe.ts`（只在 `import.meta.env.DEV` 下加载）在岛的 `island--expanded` 切换后记 700ms 的 rAF 时间，算首帧、最长一帧、中位数、掉帧（超过中位数 1.5 倍）和页面挂上的时刻，写进数据目录的 `frontend-errors.log`（`kind=island-frames`）。用实验台接口 `POST /v1/dev/island/action` 自动开合，每页 5–8 轮。rAF 只看得到网页主线程；GPU 进程里的栅格化看不到，录屏核对没做成（`screencapture` 要用户点系统权限）。

| 条件 | 700ms 内帧数 | 打开最长一帧（中位数 / 最差） | 每次打开掉帧 | 页面挂上 |
| --- | ---: | --- | ---: | ---: |
| 原状（Fuyu 面板页，冷打开） | 40–43 | 28–38 / 55 ms | 2–3（按 60Hz 算） | 32–51 ms |
| 原状，收起后 150ms 内再开（页面还在） | 84 | 11–17 ms | 0–1 | 6–11 ms |
| 解除 60fps 上限 + 页面保温（本轮改动后） | 83 | 14 / 29 ms | 1.2（按 120Hz 算） | 已挂好 |

结论：

1. **WebKit 把岛压在 60fps**。屏幕是 120Hz，岛里的 rAF 却一直 16.7ms 一帧：WKWebView 默认开着「页面渲染贴近 60fps」（`PreferPageRenderingUpdatesNear60FPSEnabled`），外壳的宽高圆角是主线程上的注册变量过渡，跟着只走 60fps，在 120Hz 的系统界面旁边显得一顿一顿。关掉后 rAF 是 8.3ms。一直关着的代价：收起的岛闲着时有循环动画，GPU 进程从约 7% 涨到约 17%、WebContent 从约 15% 涨到约 22% CPU。所以只在开合时关：`useFollowDisplayRate` 在展开或鼠标移上收起的岛（预热）时调 `set_webview_follow_display_rate(true)`，收起 700ms 后恢复，闲着时的 CPU 回到原来的水平。这个开关是 `WKPreferences` 的私有接口（`_features`、`_setEnabled:forFeature:`），系统没有这个特性时什么都不做。
2. **冷挂载是主线程上最大的一块**：同一页，页面已挂好时打开不掉帧，冷挂载时掉 2–3 帧。收起后页面保留 2 分钟（`KEEP_WARM_AFTER_CLOSE_MS`）再卸载：保温期间页面隐藏、不绘制，组件的 `panelInterval` 定时器照旧在收起时暂停；不走 `panelInterval` 的定时器在这 2 分钟里继续跑。超过 2 分钟、从没打开过、或换到别的页时仍是冷挂载。
3. **A（动画期间给展开层单独合成层）不做**：试了一段不改外观的 `translate` 动画撑合成层，打开首帧和掉帧与不加时差不多（16.7 / 2.7 对 15.5 / 2.3），rAF 看不出收益，又多一个整面板的合成层，撤掉。
4. **C（减轻「灵动」的模糊）不做**：模糊 10px 和 0 在主线程上分不出差别，模糊交给合成器算，保持用户选的样子。
5. 收起的岛闲着时开发版 WebContent 仍有约 15% CPU（60fps 下），说明收起条上有东西一直在动，另查。

### 闲置后第一次打开卡（2026-11-21，开发版）

现象：岛闲置一会儿后，第一次点开面板明显卡一下，紧接着再开就不卡。

量法：帧探针加了两项。一个 MessageChannel 忙等循环记 200ms 内最长一次消息间隔（`busy`），用来区分是网页主线程在忙还是消息根本送不进来；另记最近一次 `pointerdown` 和窗口 `focus` 离开合多久。卡的那次首帧 70–100ms，`busy` 和首帧差不多一样长。可 Time Profiler 里 WebContent 和 UI 进程的主线程那段时间都不在跑，说明网页主线程在等别的进程。在一次 99ms 的卡顿里用 `sample` 抓 UI 进程（`fuyu`）主线程，堵在 `get_device_use` → `microphone_apps` → `audio_devices::recording_pids` → CoreAudio `AudioObjectGetPropertyData`：它同步问 coreaudiod 哪些进程在录音。

原因：`get_device_use` 是同步的 Tauri 命令，Tauri 2 把同步命令放在主线程上跑。摄像头和麦克风提示每 2 秒轮询一次，平时一次约 25ms（10 秒空闲采样里 UI 主线程 130 个样本有 125 个在它里面）；闲置后 coreaudiod 醒得慢，一次能到 100ms。WKWebView 的消息派发和图层提交都要经过 UI 进程的主线程，它被堵住时网页的 rAF 和消息全停，正好碰上的那次打开就卡。刚卡过一次 coreaudiod 已经醒了，所以再开不卡；「闲置后第一次」只是撞上慢调用的概率最大。

改法：`get_device_use` 改成 `async`，在 tokio 线程上跑（macOS 和 Windows 一样改，Windows 读注册表的那份也是同步阻塞）。改后 10 秒空闲采样里主线程上不再有它。

| 条件 | 次数 | 出现超过 34ms 一帧的次数 | 打开最长一帧 |
| --- | ---: | ---: | --- |
| 改前（带 `busy` 的全部记录） | 46 | 13 | 最差 70–100 ms |
| 改后，连续开合 8 轮 | 16 | 0 | 10–18 ms |
| 改后，闲置 10 / 60 / 150 秒后第一次打开 | 3 | 0 | 12 / 16 / 10 ms |

### 闲置后第一次展开没有动画（2026-11-21，开发版）

现象：闲置一会儿后第一次点开，外壳没有生长动画，直接是展开好的样子；马上收起再开就正常。帧间隔量不出来（帧照样顺），要量每帧的外壳高度：探针的 `shell=` 记前几帧和最后一帧的高度，跳过时第一或第二帧就是终值。

查到的：

1. 跳过时外壳的宽、高、下圆角三个 CSS 过渡都在（`getAnimations()` 能拿到，时长、曲线都对），但要么关键帧是空的，要么起始时间是几秒前，要么计时正常却不再作用到元素上（`--island-shell-height` 的计算值已是终值，进度才 1%–7%）。窗口大小、页面可见性、样式表增删、120Hz 开关、冷挂载、`CSS.registerProperty` 重新登记都排除过。
2. 最稳的复现是页面重载后的第一次打开（6 次跳 5 次）。展开那次提交里 `usePagePill` 在 `useLayoutEffect` 里同步量页签位置，逼 WebKit 在渲染更新之外算样式，过渡这时被创建；把它挪到下一帧后降到 6 次跳 2 次。其余的触发点没再逐个找（提交里还有别的组件同步量尺寸）。
3. 用 Web Animations 按同样的关键帧、时长、延迟和 `linear()` 曲线另起一个动画，WebKit 会正常播。

改法：`useShellMotionGuard`（只在 macOS）在每次开合的第一帧，给这几个外壳过渡各叠一个同样参数的 Web Animations 副本。CSS 过渡照常跑、照常发 `transitionrun` / `transitionend`（原生玻璃同步靠它们），画面以副本为准；原过渡失效时动画照样完整。关键帧丢了的，用上一次停稳时读到的值做起点。改后重载后的第一次打开 6/6 正常，普通开合 8/8、刚展开 150ms 就收起也连贯；用户确认闲置后第一次点开不再跳。
