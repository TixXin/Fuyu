# 一次发版的耗时（v0.3.12-beta.4）

> 日期：2026-11-22，Mac 上的会话。从用户说「推 和 发beta」到 Release 公开，每一步花了多久、时间花在哪、怎么省。时间来自会话记录、PR 和 GitHub Actions 的起止时间、Release 资产的上传时间和 `pnpm release` 的日志（日志本身没有时间戳，几处只能按前后事件推算，表里标了「约」）。下面的时刻都是 UTC。之前的一次实测（v0.3.7-beta.2，本机编译时期）见 [docs/research/release-pipeline.md](../research/release-pipeline.md)。

## 结论

- **总耗时 80 分钟**：13:08:26 开始，14:28:31 公开；`pnpm release` 收尾到 14:31:18（83 分钟）；漏推的分享图补发到 14:34:20（86 分钟）。
- **其中「推」占了 49 分钟**，理想情况一轮验证加一轮 CI 约 16 分钟。多出的 33 分钟来自两件事：
  - 推到一半，用户要求等工作区里没提交的改动一起进这一版，多了一轮验证和一个作废的 PR。
  - 回归页 `island-resize` 的一项检查在 CI 上时好时坏：两个 PR 的 CI 共挂了 3 次，又开了一个会话去修（已修好，D118）。
- **其余 31 分钟**：
  - 等用户确认发布说明，10 分钟。规则要求的，但可以和 CI 并行。
  - 发版 PR 加 CI 预构建，10 分钟。
  - `pnpm release` 12 分钟，其中约 6 分钟花在下载两份预构建产物并签名。
- **按下面的建议做，同样一次发版约 35 分钟**，省一半以上。最划算的三条：
  - 推之前先清点没提交的改动。
  - 在最后一轮 CI 期间就写好说明、给用户确认。
  - 回归页的 CI 拆成并行分片。

## 优化建议

按省下的时间排。

1. **推之前先清点没提交的改动，问清要不要进这一版**（省约 8 分钟）。
   - 这次先 land 了已有的提交，用户再要求等工作区的改动，结果多一轮验证和一个作废的 PR。
   - 做法：发版和推 PR 的第一步先跑 `pnpm tasks dirty`。有别人在改的文件，就问用户要不要等，等它们提交了再 `mq:verify`。
   - 写进 `fuyu-release` skill 的第 1 步。
2. **在最后一轮 CI 期间就写好说明、请用户确认**（省约 9 分钟）。
   - 写说明只依赖要发的提交列表。确定要推的批次后，就可以在发版目录基于本地 `main` 起草并请用户确认，和 CI 的 9 分钟重叠。
   - 合入后在新的 `origin/main` 上重跑 `pnpm release:version`，把写好的说明拷过来；提交列表有变化时只补新增的条目。
3. **回归页的 CI 拆成并行分片**（每轮省约 4–5 分钟；这次 5 轮，最多省约 20 分钟，以后每个 PR 都受益）。
   - 每轮 CI 的关键路径都是 regression 这一个 job，8.5–9 分钟，其余 job 都在 4.5 分钟内完成。
   - 按页面拆成 2–3 个 job 并行（`run-regression.mjs` 按页名分组即可），CI 能降到约 4.5 分钟。
   - 本机 `mq:verify` 的回归页同理，加大并发或分组，能从 7 分钟降下来。
4. **时好时坏的检查尽早修，或让 `mq:wait` 自动识别**（这次约 20 分钟）。
   - island-resize 这项检查在这次之前就挂过两次（main 上一次、别的 land PR 上一次），一直没人跟进。
   - 建议 `mq:wait` 在 CI 挂了时，查同一页在最近几次 main 和 land 的 CI 里有没有挂过：
     - 挂过的标成「疑似时好时坏」，并提示开任务。
     - 没挂过的照常当真失败处理。
   - 这次的检查已由 D118 修好（`da1819207`）。
5. **预构建产物提前下载、两份并行**（省约 5 分钟）。
   - `pnpm release` 现在等到 PR 合入才开始，依次下载 Windows、Mac 两份产物，约 6 分钟。
   - 预构建跑完时发版 PR 多半还在等 CI，可以让 `release:prebuild` 在后台等两个构建跑完，就把产物下载、签名到 `target/publish`，记下哈希。`pnpm release` 发现树一致、哈希对得上就直接用。
   - 下载慢有可能是本机网络。先加第 6 条的计时，确认是下载慢还是排队慢。
6. **`pnpm release` 的日志加时间戳和阶段汇总**。
   - 现在日志没有时间，这份复盘只能用 Release 资产的上传时间倒推。
   - 每个 `✓` 行前加相对开始的时间，结束时打一张各阶段耗时表，下次复盘直接看日志。
7. **`mq:wait` 遇到网络错误自动重试**。
   - 这次 GitHub 接口断连一次，`mq:wait` 直接退出，要手动再开。
   - 读 PR 状态失败时，应按间隔重试几次再报错。
8. **发版 PR 的 CI 不用为它提速**。它跑全量回归页要 9 分钟，但同时在跑的预构建要 10.5 分钟，关键路径是预构建，单独给发版 PR 走快速通道只省约 1 分钟。
9. **已修**：分享图没推给机器人。
   - 原因是本机没设 `FUYU_BOT_INBOX`，脚本悄悄跳过了。
   - 已在 `~/.zshenv` 设好；`release.mjs` 没设时会提示（`554cec5b7`）；skill 要求发版前确认这个变量。

按 1、2、3、5 做，同样内容的一次发版大致是：

| 步骤 | 时间 |
|---|---|
| 清点工作区 | 1 分钟 |
| 一轮 `mq:verify` | 5 分钟 |
| land 后跑分片的 CI，同时写说明、请用户确认 | 5–10 分钟 |
| 发版 PR，以预构建为关键路径 | 10.5 分钟 |
| `pnpm release`，产物已提前下载 | 约 5 分钟 |
| **合计** | **约 30–35 分钟** |

## 其他可以优化的

上面的建议之外还有这些。按收益先做 1 和 4，再做 5 和 6。

1. **用户确认说明的同时先开始预构建**（省约 10 分钟，是剩下最大的一块）。
   - 预构建现在要等用户说「继续发布」才开始，10 分钟，是第 4 阶段的关键路径。
   - 说明会打包进程序里的版本历史页，预构建按整棵代码树比对，所以说明定稿前编的包只在说明不再改动时能用。
   - 做法：写好草稿、开始问用户时就按草稿预构建。用户直接说继续，就省下这 10 分钟；用户改了说明，就作废重编，只多跑一次 CI。
2. **把发版 PR 的几步合成一条命令**（例如 `pnpm release:pr`）。
   - 现在要手动做：更新 version-history 快照、提交、推分支、开 PR、开自动合并、逐个关掉别的 PR 的自动合并、触发预构建，合入后还要记得把那些 PR 的自动合并重新打开。
   - 省的时间不多，但每一步都可能漏，最容易忘的是重新打开自动合并。
3. **官网导入直接上传本机的文件**。`pnpm release` 手上已经有签好名的文件，`import-release.mjs` 却又从 GitHub 下载一遍再上传，约省 1 分钟。
4. **发版过程中主动报进度**。
   - `pnpm release` 有 12 分钟什么都不对外说，用户只能来问「还没发完吗」。
   - 在开始下载、冒烟测试通过、已公开、官网已同步这几处发一条通知，可以用浮屿自己的岛上消息或手机推送。
5. **Mac 包也做冒烟测试**。现在只在干净的 Windows 机器上安装并启动一次，Mac 的 dmg 公开前没有验过，挡不住「装上就打不开」。
6. **签名绑定版本号**。
   - 日志每次都提示 `Signing without an app version`：签名没有绑版本号，挡不住把旧版的包冒充成新版发出去。
   - 签名时加 `--app-version` 就行，但要先确认已装的客户端认这种签名。
7. **升级 GitHub Actions**。
   - 每次构建都提示 `actions/checkout@v4`、`actions/setup-node`、`actions/upload-artifact@v4` 还在用 Node 20，现在是被强制跑在 Node 24 上。
   - 在被彻底停用前升到新版本，免得哪次发版时构建突然挂掉。

## 建议的任务

- 发版前清点没提交的改动、提前写说明（建议 1、2）：已写进 `fuyu-release` skill 第 1 步。
- CI 和本机回归页分片（建议 3）。
- `mq:wait` 识别时好时坏的检查，遇到网络错误自动重试（建议 4、7）。
- 预构建产物提前下载、并行下载，`pnpm release` 日志加计时（建议 5、6）。
- 确认说明时就开始预构建、发版 PR 合成一条命令、官网导入用本机文件（「其他可以优化的」1–3）。
- 发版过程中通知进度（其他 4）。
- Mac 冒烟测试、签名绑定版本号、升级 GitHub Actions（其他 5–7）。
