## 说明

Tauri 的 `emit` 把负载内联进一段脚本交给 WebView 执行，每个内容不同的负载就是一段新脚本，强制 GC 后也不回收，约 0.75 KB 一个（tauri-apps/tauri#12724，上游是 WebView2 的问题，未修）。浮屿一直开着，每秒 1 个事件就是每天约 65 MB。Rust 侧有 83 处 `emit`，要找出其中高频的（鼠标穿透、跟随、Agent 状态、媒体、音量）。

做法：先看 D47 的长跑结果确认是否踩中。给各个事件加计数（只在诊断构建里），按频率排序；内容和上次相同的不发；确实高频的数据改成前端 `invoke` 拉取或合并成低频的批量事件。事件名是对外契约，不改名、不改负载格式。

来源见[调研](/docs/research/memory-and-performance.md)。

备注（2026-11-14，会话「Issue处理优先级」）：泄漏出在 Rust 往 WebView 执行脚本这一步；`invoke` 的回应走自定义协议 `ipc://localhost`，不经过执行脚本。高频事件除了改成按需拉取，还可以做一个通用的长轮询命令：前端挂着一个 `invoke`，Rust 有事件时作为回应批量返回。插件平台第 3 版的宿主和窗口通信也要用同样的办法（[v3-everything-plugin.md](/docs/architecture/plugins/v3-everything-plugin.md)「内存」）。

## 验收

- 有一份各事件每分钟发送次数的清单（闲置、放音乐、有 Agent 会话三种情况）。
- 闲置时每分钟发往 WebView 的不同负载数量降到个位数，或写明剩下的为什么必须发。
- 按 D47 的方法再跑一次，私有内存不再随时间线性增长。
- 事件名和负载格式不变，`pnpm test:regression` 通过。
