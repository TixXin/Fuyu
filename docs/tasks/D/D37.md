## 说明

现在的 `pnpm release` 只能在 Windows 本机跑，在 Mac 上发不出 Windows 版：

- [release.mjs](/scripts/release/release.mjs) 用宿主平台跑 `tauri build --bundles nsis,msi`。MSI 靠 WiX 打包，WiX 只能在 Windows 上跑；从 Mac 交叉编译 NSIS（cargo-xwin + makensis）在 Tauri 2 里还是实验功能，`windows` crate 的交叉编译也没验证过。缺了 MSI 不行：MSI 装的用户检查更新时要从 `latest.json` 里找 `windows-x86_64-msi`。
- 本机的更新签名密码用 Windows DPAPI 加密，[release-signing.mjs](/scripts/release/release-signing.mjs) 在别的系统上直接报错。

目标：Windows 包在 CI 出，从哪台机器（Windows 或 Mac）跑 `pnpm release` 都行。这样也和 Mac 包的出法一致（G1.13：Mac 包在 macOS runner 上出），两个平台同时发版（M12）更容易做到。

做法草案：

1. 新增 `release-windows.yml`（`workflow_dispatch`，入参为 tag 和提交）：在 `windows-latest` 上 checkout 指定提交，装 pnpm / Rust，跑和现在一样的 `tauri build --bundles nsis,msi`（带 `tauri.release.conf.json` 和 MSI 版本覆盖），把 NSIS、MSI 和各自的 `.sig` 上传到 Release 草稿。签名私钥和密码放仓库 Secrets（`TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`），公钥可以放 Variables。
2. `pnpm release` 增加一种模式（例如 `--ci-build`，或在非 Windows 上默认走这条）：本机只做校验、建草稿、触发工作流、等它跑完、下载产物，再照旧生成 `latest.json` 和 `SHA256SUMS.txt`、比对 SHA-256、跑冒烟测试、公开。Windows 本机构建的老路径先保留，作回退。
3. 把 `release-smoke.yml` 串在构建之后，或者让 `pnpm release` 照旧依次触发两个工作流。
4. 发布后把刚发的 exe 复制到 `target/release` 那一步：CI 构建时跳过（或从草稿下载），在 Mac 上不做。
5. 更新 [updater.md](/docs/features/updater.md) 的发布流程，以及 [macos-port-plan.md](/docs/architecture/macos-port-plan.md) 的 M11（原来定的是「Windows 包继续本机出」）。

## 验收

- 在 Mac 上跑 `pnpm release`（测试版）能发出完整的 Windows 版本：NSIS、MSI、`.sig`、`latest.json`、`SHA256SUMS.txt` 都在，冒烟测试通过。
- CI 出的包的更新签名能被已安装的旧版本验证通过，从上一个测试版自动更新到这个版本成功。
- `latest.json` 的 `windows-x86_64-nsis`、`windows-x86_64-msi`、`windows-x86_64` 三项都在，和本机出包时的格式一致。
- 签名私钥只在 Secrets 里，不出现在日志和产物里。
- 在 Windows 本机按原来的方式发版仍然可用。

## 备注

- 要用户本人做：把签名私钥和密码填进仓库 Secrets，并确认 M11 改成「Windows 包也在 CI 出」。
- CI 每次全量编译 Rust，单次大约 15–25 分钟；可以用 `Swatinem/rust-cache` 缓存。
- 2026-11-13 用户问能不能在 Mac 上发 Windows 版，结论是不行，因此建这个任务。
