## 说明

2026-11-13 实测 3072×1728：把约 2100 万字节的画面经 IPC 传进页面再 `putImageData` 要 260–380 ms（debug）。窗口已经先显示，但这段时间里取色、放大镜、带标注的完成都不能用。试几种做法再定：传压缩后的图（PNG / QOI / WebP 无损）交给 `createImageBitmap` 解码、按显示器分块传、或用自定义协议让页面直接取。先量再改，数字写进备注。

## 验收

- release 版 4K 单屏从按下快捷键到放大镜可用的时间有前后对比数字，目标 150 ms 以内
- 多显示器、混合缩放下画面位置不变
- `pnpm check`、`pnpm build`、`cargo test`、`pnpm build:exe`

## 备注

### 2026-11-20 Mac 上先量（shot-batch1）

探测程序 `src-tauri/examples/screenshot_frame_probe.rs`：一个独立的 Tauri 窗口，用自定义协议把一帧整屏 RGBA 交给页面（和 `screenshot_frame` 走的 `ipc://` 原样返回是同一条路），每种做法先热身一轮再跑 6 轮取中位数，结果打印到终端后自己退出。命令：

```bash
pnpm heavy -- cargo build --release --manifest-path src-tauri/Cargo.toml --example screenshot_frame_probe
src-tauri/target/agents/release/examples/screenshot_frame_probe <一张真实截图.png>
```

MacBook Air 外接 4K 屏，release，3840×2160（3300 万字节），WKWebView，单位 ms：

| 做法 | 取到字节 | 画上 canvas | 到下一帧画面 | 其他 |
|---|---|---|---|---|
| 原样传 + `putImageData`（现在的做法） | 17 | 11 | 43 | Rust 复制 2.3 |
| 原样传 + `createImageBitmap` + `drawImage` | 17 | 22 | 49 | |
| 分 4 块并行取 + `putImageData` | 15 | 14 | 43 | |
| PNG（快速压缩，400 万字节）+ `createImageBitmap` | 6 | 149 | 173 | Rust 编码 43，取回像素给取色再要 6 |

结论：Mac 上原样传已经是最快的，压缩反而慢 4 倍，传输和绘制合起来不到 50 ms，不用改。任务说明里的 260–380 ms 是 debug 版（多半还是 Windows），release 不是这个量级。

同一台机器上，`macos/screen_capture.rs` 的 `capture` 截主屏 3840×2160（debug，含每次重新取 `SCShareableContent` 和 BGRA→RGBA 换算）：第一次 780 ms，之后 170–225 ms。所以 Mac 上「按下快捷键到放大镜可用」大头在截屏本身，不在送进页面；要往 150 ms 以内压，下一步看截屏：release 下换算的耗时、能不能复用 `SCShareableContent`、冷启动那一下能不能在启动时预热。

还没做：Windows（WebView2 的自定义协议大响应一向慢，最可能就是那 260–380 ms 的来源）上跑同一个探测程序；两个平台在真岛上量「快捷键到放大镜可用」的端到端数字。Windows 上如果原样传明显慢，候选是 WebView2 的 `PostSharedBufferToScript`（共享内存，零复制）。

### 2026-11-25/26 实测与实现（shot-frame，Apple M4 macOS arm64）

#### 1. 传输编码 & BGRA→RGBA 实测（release，`screenshot_frame_probe`，4K `3840×2160` = 33,177,600 B）

- **合成桌面图**：
  - `raw + putImageData`: `fetch 11.0  draw 6.0  painted 33.0  rust 1.6 ms`
  - `async-raw + putImageData`: `fetch 13.0  draw 6.0  painted 34.0  rust 3.4 ms`
  - `raw + createImageBitmap`: `fetch 11.0  draw 24.0  painted 38.0 ms`
  - `parts4 + putImageData`: `fetch 7.0  draw 7.0  painted 33.0 ms`
  - `bmp + createImageBitmap + readback`: `fetch 10.0  draw 73.0  painted 95.0  readback 5.0  bytes 33,177,722`
  - `qoi + putImageData`: `fetch 1.0  decode 13.0  draw 6.0  painted 33.0  rust 4.6  bytes 2,045,787`
  - `png + createImageBitmap + readback`: `fetch 1.0  draw 56.0  painted 59.0  readback 4.0  rust 9.5  bytes 802,280`
  - `webp + createImageBitmap + readback`: `fetch 0.0  draw 44.0  painted 46.0  readback 4.0  rust 15.1  bytes 351,532`
- **纯噪点 4K `--noise`**（最坏不可压缩场景）：
  - `qoi + putImageData`: `painted 50.0 (rust 33.7, decode 33.0, 32.3 MB)`
  - `png + bitmap`: `painted 149.0 (14.4 MB)`；`webp + bitmap`: `painted 120.0 (7.3 MB)`
- **BGRA→RGBA 换算（3840×2160）**：`old_with_copy 9.22 ms` → 零拷贝 `as_bytes_unchecked()` + 对齐 `u32` 换序 `fast_u32_nocopy 2.38 ms`（并省掉 33 MB 临时分配）。

#### 2. 真实 `dist/index.html?window=screenshot` 选区窗口端到端（`--features tauri/custom-protocol --real-overlay`，3840×2160，`Magnifier` 就绪）

- **优化前基准**（不含抓屏时间）：`300.5 ms`（`window_build_call 28.5 ms`，`DOMContentLoaded 174.5 ms`，`session_req 234.9 ms`（且重复调用 2 次），`frame_start 258.8 ms`，`frame_send 267.7 ms`，`canvas_rel 227.0 ms`，`magnifier_rel 231.0 ms`）。
- **改动**：
  1. **Windows WebView2 共享内存直传**（`src-tauri/src/win32/webview_shared_buffer.rs` + `src/features/screenshot/framePrefetch.ts`）：`screenshot_frame` 在 Windows 上通过 `ICoreWebView2Environment12::CreateSharedBuffer` + `ICoreWebView2_17::PostSharedBufferToScript` 投递 RGBA 与 `{ id, width, height }` 元数据并立即 `shared.Close()`，JS 侧 `sharedbufferreceived` 拷出后在 `finally` 调 `releaseBuffer`，`screenshot_frame` 返回空 `0` 字节响应；旧运行库或异常自动回退原 `Response` 字节通道，保留 D124 退出即销毁选区窗口与每显示器独立缩放/坐标系。
  2. **Rust 会话与抓屏并发**（`src-tauri/src/screenshot/session.rs` + `macos/screen_capture.rs`）：`session::open` 先发布初始 `Session` 计划帧，再用 `thread::scope` 同时并发跑多屏抓屏、`targets::windows_on_screen` 和 `place_windows`；严格保持选区窗口 `.visible(false)` 直到 `session.captured == true`，`finish_grabs` 拿到像素即唤醒 `CAPTURED` 不等窗口控件枚举，Mac `screenshot::init` 在已有录屏权限时后台预热 `SCShareableContent`。
  3. **前端首帧瘦身与秒起预取**（`vite.config.ts`、`src/i18n/runtime.ts`、`src/i18n/devFallback.ts`、`src/main.tsx`、`src/windowServicesLoader.ts`、`src/windows/screenshot/useScreenshotFrame.ts`）：构建期剥离全量 `translations.ts` / `devFallback.ts` 回退并把 `i18n-core`（257 KB）从主入口（557 KB → 233 KB）拆出；`?window=screenshot` 首屏仅加载 `sections/screenshot.ts` + `common.ts`（约 15 KB），`main.tsx` 顶层立即并发发起 `screenshot_session` + `screenshot_frame`（消除二次 `session_req`），`useScreenshotFrame` 用 `useState` 初值 + `useLayoutEffect` 首轮 `putImageData`（`alpha: false`）并延后 250 ms 加载完整 i18n、字体、设置文件与插件服务。
- **优化后实测**（`--features tauri/custom-protocol --real-overlay`，3840×2160）：
  - 入口与打包前对比：入口 JS `557 KB → 228–233 KB`；首屏 i18n 负荷 `268 KB → 15 KB`。
  - 未受打包并发争用时（`task-555`）：两次连续运行分别 **`151.7 ms`**（`ready_cmd 132.2 ms`, `canvas_rel 63.0 ms`, `magnifier_rel 75.0 ms`）与 **`131.7 ms`**（`window_build_call 28.5 ms`, `DOMContentLoaded 69.4 ms`, `frame_send 70.7 ms`, `ready_cmd 101.5 ms`, `canvas_rel 52.0 ms`, `magnifier_rel 68.0 ms`）。
  - 完整精简后（`task-630`，后台仍有并发检查负载下）：warm 运行 `144.2 ms`（`ready_cmd 133.4 ms`）与 `150.5 ms`（`ready_cmd 136.8 ms`）；机器极高负载（`load avg 143`）下首帧启动升至 `209–280 ms` 属于本机并发编译 CPU 争用。
