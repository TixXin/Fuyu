## 说明

`plugins.yml` 里 `source: dev`、`path` 指向数据目录之外的开发插件，宿主显示在跑，但岛的页头、收起条和设置里都没有它，也不报错。`fuyu-plugin dev` 默认把产物放在插件项目旁边，几乎一定在数据目录之外，第三方作者照文档 `npm run dev` 都会撞上。

原因：宿主给数据目录外的 dev 来源登记了前缀 `dev/<id>/`（`packages/plugin-base/src/host/kernel.mjs`、`clients.mjs`），但 Rust 的 `fuyu-plugin://` 只从数据目录取文件（`src-tauri/src/plugin_kernel/protocol.rs`），`/dev/<id>/...` 一律 404；`v3-builtins.md` 写的「Rust 一侧的映射同上」没有实现（E36.3.9 遗留）。

改法：
- Rust 加上 `dev/<id>/<相对路径>` 的映射，根目录来自宿主的 clients 通知（`{ prefix, dir }`）或 `plugins.yml` 里 `source: dev` 的条目，二选一并写明理由；规范化后不能跑出根目录，只放行宿主登记过的界面文件。
- `clients.locate()` 返回 null 时，插件状态带上明确的问题，插件页能看到原因，不再悄悄失败。
- `builtin/<id>/` 不做（内置插件界面打包在程序里），改对 `v3-builtins.md` 那一行的状态。

## 验收

- 数据目录外的开发插件，窗口部分在 Windows（`http://fuyu-plugin.localhost/`）和 Mac 上都能加载
- `protocol_tests.rs`：登记过的能取到，没登记的和跑出根目录的仍是 404
- 文件不在任何能读的根目录里时，插件页显示原因
- Rust 单元测试、`pnpm build:exe`、`pnpm check` 通过，附 `pnpm mq:try` 的 Windows run

## 备注

- 根目录来源选「宿主的 clients 通知」，不让 Rust 读 `plugins.yml`：宿主已经把 `path` 按数据目录解析成绝对路径、`realpath` 过，也知道插件有没有被拒、在不在跑；Rust 再读一遍就是第二份解析，相对路径、被拒和停用的条目都可能和宿主对不上。安全上也不差：`plugins.yml` 本来就在宿主能写的数据目录里，Rust 自己读并不更可信。通知里的 `roots` 只收 `dev/<id>`（一段或两段）前缀和绝对路径，宿主只报 `paths` 里真用到的前缀。
- Rust 的放行规则和数据目录一样按「登记文件所在的那一层文件夹」：登记 `dev/clock/dist/island.js` 只放行开发文件夹里的 `dist/`，`package.json`、`.env`、`src/`、`node_modules/` 都是 404。路径里的 `..`、`\`、`:`（盘符）、空段（`//server` 这种 UNC 写法）一律拒绝，符号链接解析后必须仍在开发文件夹里，落进数据目录的也拒绝。
- `clients.locate()` 返回 null 的情况在宿主里其实只剩一种：已安装的包被链接到数据目录外（`installedRoot` 会 `realpath`）。开发来源总有 `dev/<id>` 前缀，文件在清单校验时就保证在开发文件夹里。
- `builtin/<id>/` 不做：内置插件的界面和程序一起打包，由程序前端加载，不经 `fuyu-plugin://`；`v3-builtins.md` 那一行已改。
- 验证（Mac）：Rust 单元测试 1233 通过，clippy `--all-targets -D warnings` 0 告警，`pnpm build`、`pnpm build:exe` 通过，`pnpm check` 各步通过（`pnpm test` 1698 通过），`pnpm test:regression plugin` 8 页通过（plugin-page 两页快照按新增一行更新）。
