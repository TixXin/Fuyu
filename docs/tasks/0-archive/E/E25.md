## 说明

`TixXin/fuyu-plugins` 的 CI 现在只把 zip 解压后重新打包、比较哈希（[packages.mjs](https://github.com/TixXin/fuyu-plugins/blob/main/scripts/lib/packages.mjs) 的 `inspectPackage`）。这只能说明包是 `fuyu-plugin pack` 打的，而且不一致也只是警告。

维护者审核时读的是仓库在那个 tag 的源码。没有任何一步保证 zip 里的内容和它相同：作者，或者拿到他账号的人，可以让 Release 附件带着仓库里没有的代码。首版之后的版本只要不新增权限就自动上架，不再有人看。

`fuyu-plugin pack` 的输出是确定的，所以 CI 可以自己核对：取仓库在 Release tag 处、`path` 文件夹里的文件，用同一个 `pack` 打包，和 Release 附件比较 SHA-256。

- 一致：照常上架，PR 检查摘要里记一笔。索引条目可以加一个可选字段（例如 `"sourceMatch": true`），岛屿和官网以后能显示「与源码一致」。索引加字段是对外契约，登记到 [contracts.md](/docs/architecture/contracts.md)；岛屿的 `MarketEntry` 不拒绝未知字段，旧版照常。
- 不一致：首次提交的 PR 检查失败；已上架插件的新版本暂缓上架并开 `review-needed` issue，和「申请了新权限」一样等维护者处理。
- 有构建步骤的插件（TypeScript 编译出的 JS 不在仓库里）做不到一致。先看脚手架的 TypeScript 模板怎么打包再定规则：要求把构建产物提交进仓库，或者允许在提交文件里声明有构建步骤、这种插件每个版本都人工看。
- 官方插件用固定的 `package` 地址，没有 tag。它们和源码是否一致已经由本仓库的 `pnpm test` 检查，可以跳过，或者按 `main` 核对。

2026-11-13 市场上 8 个插件都是 PowerShell、没有构建步骤，可以直接核对。

## 验收

- fuyu-plugins 的测试覆盖：一致、zip 里多了文件、文件内容不同、tag 不存在。
- 对现有的 8 个插件跑一遍，结果写进这个任务的结论。
- fuyu-plugins 的 CONTRIBUTING.md 和 [publish.md](/docs/plugins/publish.md) 写明这项检查，以及不一致时怎么办。

## 结论（2026-11-14）

在 TixXin/fuyu-plugins#22 实现：取 Release 标签处的源码用 `fuyu-plugin pack` 打包，和附件按文件比较。只比 zip 字节不行：现有两个第三方插件的文件完全一致，但它们的 zip 是旧版 `pack` 打的，字节和新版不同。

| 插件 | 结果 |
|---|---|
| 6 个官方插件 | 固定地址、没有标签，跳过（由本仓库的测试保证一致） |
| `io.github.shenglin1001.battery` 1.0.0 | 按文件一致 |
| `io.github.shenglin1001.timesync` 0.1.0 | 按文件一致 |

有构建步骤的插件：市场不运行作者的构建脚本（索引任务里有签名密钥），在描述文件里写 `"buildStep": true` 跳过核对，条目不带 `sourceMatch`。现在市场上没有这类插件。
