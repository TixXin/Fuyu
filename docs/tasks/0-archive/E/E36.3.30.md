## 备注

### 做了什么

- 拥有者：`plugin/owner.ts` 导出 `OWNER = "calendar"`，岛上的日历页（`plugin/island.tsx`）和设置 → 日历（`plugin/settings.tsx`）都挂在它名下，关掉日历插件时一起撤掉。
- 旧开关：`calendarEnabled` 在 `LEGACY_SWITCHES` 加一行。备份经镜像自动带上，没有别的存储里的开关。
- 后台：日历在 Rust 里没有线程（命令被调时才读，缓存 15 分钟），`builtins.json` 的 `background` 照旧是 `[]`，加了一条测试核对。关掉后岛不再轮询 `get_calendar_events`，原因是 `IslandApp` 的 `useCalendar` 读的是 `LEGACY_SWITCHES` 镜像出来的 `calendarEnabled`。
- 服务 `calendar/v1`：`events({ refresh? })`、`sources()`。宿主那份由 `host/index.mjs` 调 Rust 方法 `calendar.events`、`calendar.sources`（`#[host_service]`，`inject(app)`），窗口那份在 `plugin/services.ts`；两边都经 `host/index.mjs` 的 `serviceEvents`、`serviceSources` 规整成同一个形状。`sources` 不带账号、地址和订阅链接。读不到的日历记进 `problems`（`{ sourceId, reason, message }`），不让整个调用失败。
- **计划第 1 批表里「会议行改经插槽」挪给了 E36.3.51**（组长 2026-11-15 定）：会议行、`useMeetingBeat`、`openTarget` 和 `useCalendar` 往两处传的状态都是外壳拿功能状态算布局，跟着通用贡献元数据一起改，已记进 E36.3.51 的说明。这次没碰外壳。

### 给样板写法表补的几条

- **服务的类型和生成的 Rust 类型重名**：`gen:rust-types` 把 `#[host_service]` 结果里的结构体（这里是 `CalendarEvent`、`CalendarEvents`、`CalendarProblem`）导出到 `generated/rust.d.mts`，`index.d.mts` 又 `export *` 了服务的声明文件，同名就是 TS2308。服务的声明直接 `export type { … } from "../generated/rust.mjs"`，不要再写一份；Rust 结构体名和服务里只给 JS 用的类型名错开（这里 Rust 叫 `CalendarSourceInfo`，服务叫 `CalendarSource`）。
- **`i64` 字段**：ts-rs 默认把 `i64` 生成成 `bigint`，毫秒时间戳要加 `#[cfg_attr(test, ts(type = "number"))]`。
- **`UserError::code()` 只在测试构建里有**：release 里要错误码就从序列化结果读（`calendar::reason_of`），不然 `cargo test` 过、`build:exe` 编不过。
- **方法没有参数时**：`ServiceClient` 不支持可选参数，`events(params?: …)` 会让 `calendar.events()` 报错；写成 `events(params: { refresh?: boolean })`，调用时传 `{}`。
- **宿主和窗口共用规整函数**：窗口那份拿到的是原来 Tauri 命令的形状（`problems[].message` 是 `NativeError`），宿主那份拿到 Rust 方法的形状，两边都过 `host/index.mjs` 里同一个纯函数，保证服务的回答一样。
