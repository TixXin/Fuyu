## 说明

Rust 测试程序在 Windows 上没有嵌 manifest：静态登记的代码直接或间接用到 `AppHandle`，测试程序就链进 tauri 运行时、导入 comctl32 v6 才有的 `TaskDialogIndirect`，一启动报 `0xc0000139`，一个测试都不跑。第 3 阶段挂过两次（日历 `inject(app)`，c811bcbf 修；文件中转方法体间接调 `emit_to` / `publish_event`，dbe0cc6e 修）。[E36.3.53](/docs/tasks/0-archive/E/E36.3.53.md)（#644，76bef18d）让宏拒绝 `AppHandle` 参数，但挡不住间接调用，本机也查不出，只能靠 Windows CI 兜底（规则见 f2e4f944 改的 [v3-services.md](/docs/architecture/plugins/v3-services.md)）。插件系统总控 2026-11-16 定：根治，但不放进第 3 阶段。

做法：`tauri-build` 改用 `WindowsAttributes::new_without_app_manifest()`；在 `src-tauri/build.rs` 里用 `cargo:rustc-link-arg`（`/MANIFEST:EMBED /MANIFESTINPUT:<manifest 文件>`）给所有目标（含测试程序）嵌同一份带 Common-Controls v6 的 manifest，内容和 tauri 现在默认嵌的一致。

风险：正式程序的 manifest 也跟着换，只能在 Windows 真机和 CI 上验证，Mac 上验不了。

## 验收

- 故意在一个 `host_service` 的方法体里间接用 `AppHandle`，Windows CI 的 Rust 单元测试不再出现 `0xc0000139`（验完去掉试验代码）
- 正式包 `fuyu.exe` 的 manifest 和改之前对比，DPI 感知和 common controls 都不变（真 Windows 上导出对比）
- 放宽 `v3-services.md` 里「服务方法走到的代码里不能有 AppHandle」这条规则

## 备注

- 做法：`src-tauri/build.rs` 改用 `tauri_build::try_build(Attributes::new().windows_attributes(WindowsAttributes::new_without_app_manifest()))`，目标是 Windows MSVC 时输出 `cargo:rustc-link-arg=/MANIFEST:EMBED` 和 `/MANIFESTINPUT:<src-tauri/windows-app-manifest.xml 的绝对路径>`；manifest 文件照抄 tauri-build 2.7.4 的默认那份（只有 Common-Controls 6.0.0.0 依赖）。gnu 目标和 Mac 不输出。没加 `/MANIFESTUAC:NO`：链接器默认加的 `trustInfo asInvoker` 和没有这段时的行为一样。
- Windows CI 证明（两轮，试验代码都没进 main，跑完删了 try 分支）：
  - A：`dbe0cc6e^`（8f4a9572，文件中转修之前）原样 → Windows `rust` 失败，`fuyu_lib-….exe (exit code: 0xc0000139, STATUS_ENTRYPOINT_NOT_FOUND)`：https://github.com/TixXin/Fuyu/actions/runs/43840992421 （当年同样的失败：https://github.com/TixXin/Fuyu/actions/runs/43827812883 ）
  - B：同一基点加本修复 → 全绿，主测试程序 1132 passed：https://github.com/TixXin/Fuyu/actions/runs/43840991924
  - 先试过在 `app.echo` 方法体里经普通函数从 `OnceLock<AppHandle>` 取出来 `emit_to`，Windows CI 没触发（run 43839726001）：只把 `emit_to` 留进测试程序不够，要走到导入 `TaskDialogIndirect` 的代码。
