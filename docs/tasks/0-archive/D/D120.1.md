## 说明

- `scripts/test-changed.mjs` 调回归页时没带 `--jobs`，默认 1 个浏览器；`mq:verify` 用 3 个。改成并行（3 个或按核数算）。
- `scripts/heavy/queue.mjs` 的名额是 `floor(核数 / 5)`（10 核 Mac = 2 个），回归页、`cargo`、`build:exe`、`verify` 共用。让回归页单独排队或按浏览器数算名额，同时给浏览器总数设上限。

见[调研](/docs/research/pre-commit-test-speed.md)「结论」第 1 条。

## 验收

- `test:changed` 挑出几十页时多个浏览器并行跑，输出写明开了几个。
- 回归页和 Rust 构建同时排时，回归页不用等 Rust 构建让出名额；全机器同时开的浏览器有上限。
- 同样规模的一次提交实测时间写进备注。

## 提交

- `test(changed): run the picked regression pages in three browsers`
- `feat(heavy): give regression pages their own browser queue`

## 备注

实测（2026-11-22，10 核 Mac，`node scripts/test-changed.mjs src/i18n/sections/island.ts`，38 个单元测试文件 + 全部回归页）：

| | 回归页 | 浏览器 | 排队 | 总耗时 | 每页 |
|---|---|---|---|---|---|
| 改前 | 78 页 | 1 个 | 0（当时队列空，另有一个 clippy 占着名额） | 478 秒 | 6.1 秒 |
| 改后 | 100 页 | 3 个 | 0（两个 Rust 名额都被占着、还有一个在排，回归页照样直接开跑） | 215 秒 | 2.1 秒 |

- 改后页数多是因为同时另一个会话没提交的 `scripts/run-regression.mjs` 加了页，两次的页不完全一样；按每页算快了约 2.8 倍。
- 改前那次如果碰上 Rust 名额被占满，还要再加排队时间（调研里那次是 4.5 分钟）；改后回归页不再等 Rust 构建。
- 两次各有一页没过，都不是本任务的改动：改前 `settings.html`（推送/声音那一列，工作区里别的会话没提交的设置改动），改后 `settings-search.html`（`searchIndex.json` 少了 behaviorTuck 的三行，别的会话没提交的改动）。
