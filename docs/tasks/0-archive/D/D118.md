## 说明

`tests/regression/island-resize.tsx` 的「折叠岛的边亮起时只亮小拉环，不再并排多一条亮线」在 Windows CI 上时好时坏（run 44946753142、45001142187、45026580398、45027671410），本机一直通过。失败时 class 只有 `island-resize island-resize--bar`，没有 `glow-l` 也没有 `is-near-cap-l`，等满两个 2 秒的 `until` 后报错（约 4030ms）。

## 验收

- 根因查清，写进本文件和提交正文
- 本机复现失败的写法改后通过，`pnpm test:changed` 过
- 不调大超时、不加固定等待

## 提交

- `test(island): wait for the collapse to finish before hovering the bar edge in island-resize`

## 备注

根因：折叠时岛宽的过渡 `--island-shell-width` 用 `cubic-bezier(0.34, 1.36, 0.5, 1)`，会回弹。本机打点：从约 1050 收到 340 时，约 300ms 处冲到 310，再在 550ms 时回到 340；宽度按设备像素取整，一次跳 2px。页面原来用「宽度和 340 相差不到 0.5」判断折叠结束，下降途中某一帧正好是 340 时就会提前放行。之后量到的 `box` 是这一帧的瞬时值；如果量完 `box` 到派发 `pointermove` 之间隔了一帧（慢的 CI 上 `act()` 之间更容易），岛已经缩到 330 以下，`box.left + 4` 落在改尺寸层左边外面，`useResizeZones` 当成移出处理（清掉 near、不开始计时），之后再没有移动事件，边一直不亮。

复现：本机把等待改成「下降途中宽度 ≤ 342」再在量完 `box` 后插两帧，3/3 报出和 CI 一模一样的错（约 4050ms、同样的 class、拉环不透明度 0）。

修法：等待条件加上 `animationsDone(.island)`，等宽度到 340 且岛上的过渡都跑完再量 `box`、再悬停。改后在「量完插两帧」的写法下 5/5 通过、4 倍 CPU 降速下 4/4 通过（等待约 560–620ms 结束，不靠超时），干净版本连跑 20 次都过。组件不改：真实鼠标会持续发移动事件，岛停下后下一次移动就会进入边缘区。
