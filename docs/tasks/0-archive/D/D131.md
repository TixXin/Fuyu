## 说明

2026-11-27 推 PR #1303 前，try CI 的 `regression (1/3)`（Windows Server 2025）挂了一次 `notch-island.html?test=1`，失败的检查是「异步挂起加载的插件在刘海两翼迁移时稳定收进「+N」，不闪不挤扁」（`tests/regression/notch-island.tsx:331`）。本机全量回归页和下一个提交的 CI 都过了。这批提交没碰岛的代码。

这条检查同时查三件事：每个时钟完整显示、没有 `.island__collapsed-fit[data-clipped]`、有「+N」，日志看不出是哪一条不成立。相关旧修复是 `bc13e55bd`。可能是异步挂起加载后两翼重新分配晚于 `settleTransitions()`，也可能是实现在 Windows 上真会闪一下，待核实。

先拆开检查或在消息里带上实际值，再单独连跑这一页（`fuyu-testing` skill「时好时坏」）。Windows 上的跑法用 `pnpm heavy` 到 winrel，或者用 `pnpm mq:try`。

## 备注

- 根因是等待方式，不是实现：`settleTransitions()` 把页面关在一个 900 毫秒的 `act()` 里，异步时钟排下的 React 更新（15 毫秒加载、进入收起模式后重新渲染、TYO 跨到左翼重挂）全被压住，等待结束才一起放出来，检查就落在收起条还没排好的那一刻。本机埋点：检查时 TYO 刚在左翼重挂、还没渲染，岛上只有「LON NYC +2」，6 毫秒后才变成稳定的「TYO | LON NYC +2」。`every(whole)` 不管缺了的时钟，所以本机是空着通过；CI 上换个时机落到挤扁或还没出「+N」的那一步就挂。
- 改法：`pollUntil.ts` 加 `steady(read, ready)`，这一条改成每 50 毫秒查一次，等到布局连续两次一样、五个时钟都有着落（岛上个数 + N = 5）再断言；断言里也加上这条，失败消息带每个时钟的翼、宽度、被裁格数和「+N」。实现没改。
- 证明拦得住：把等待换回旧的 `settleTransitions()`，新断言 2/2 挂（`LON右44 NYC右44；被裁 0 格；「+N」+2`）。
- 单独连跑 notch-island 页：本机 32/32，本机 CPU 降速 4 倍 9/9，Windows（winrel，`pnpm heavy`）10/10，共 51 次全过。修之前单纯降速 4 倍 8 次、8 倍 4 次都复现不了。
