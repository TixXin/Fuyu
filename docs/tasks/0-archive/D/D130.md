## 说明

2026-11-27 推 PR #1298 前在 winrel 上跑 `pnpm mq:verify be1d1c537`，`pnpm verify` 第一次挂了两个插件宿主测试，同一提交 `--only verify` 重跑全过。这批改动没碰它们用到的文件。

- `tests/scripts/plugins-v3-measure.test.mjs`「startup, restart and soak each run against the real host」：第 75 行 `rows.length >= 3` 失败，CSV 只有表头加一行。测试给 `soak` 1.2 秒、每 0.5 秒采一次；`scripts/plugins-v3/measure-host.mjs` 的 `soak` 每轮先 `ping` 再 `readMemory`，Windows 上读内存走 PowerShell，一次可能就超过窗口，第二轮来不及开始。待核实。
- `tests/unit/builtins-off.test.mjs`「every built-in plugin, switched off, …」：`local-api`、`device-use` 开关一轮后各多出 1 个 Timeout。可能是插件真漏了定时器，也可能是宿主的计时器恰好落在两次 `quietHandles()` 之间。待核实。

先单独连跑看失败率和挂在哪一步（`fuyu-testing` skill「时好时坏」），Windows 上的用 `pnpm heavy` 到 winrel 跑。

## 备注

根因：

- builtins-off：`local-api`、`device-use` 的宿主入口是空的 `apply() {}`，插件不可能漏定时器。多出来的 Timeout 是宿主 `packages/plugin-base/src/host/kernel.mjs` 的 `watchConfig` 每次 `plugins.yml` 变化后排的补读（50 ms、400 ms，见 b48036a99）。测试改完配置等到状态变了、`settle()` 返回就数句柄，这时 400 ms 那次几乎总还挂着；切换慢过约 350 ms（机器忙）时它在「关之前」那次计数里已经触发、「关之后」还挂着，于是差 1。用 async_hooks 探针看到每个计数点都挂着 `kernel.mjs:44` 的计时器；在探针里切换后插 360 ms 延时，旧代码每个插件都报「left 1 Timeout behind」，新代码通过。修法：宿主 `settle()` 先等最后一次补读做完再等 loader 任务，算作宿主没做完的事。新增测试「settle returns only after the host has reread …」在旧代码上 3/3 必挂。代价：builtins-off 每次切换多等约 400 ms，Mac 上 9 s → 39 s，winrel 上约 41 s（上限 120 s）；其余 38 个调用 `settle()` 的测试文件耗时不变。
- measure soak：旧循环是「现在没过截止就再采一次」，而 Windows 上 `readMemory` 每次起 PowerShell，winrel 实测冷启动 1.5–2.8 s、热的约 260 ms；第一次采样超过 1.2 s 窗口就不会有第二次，CSV 只剩一行。修法：按第几次排采样时间（0、every、2×every…直到 minutes，共 `⌊minutes×60/every⌋+1` 次），慢了只推后下一次，不少采；长跑最后一行也不再因计时器晚到被跳过。

winrel 连跑（每次单独起 `node --test --test-name-pattern` 只跑这个测试）：

- 修复后：measure 87 次全过、builtins-off 87 次全过（3 路并发 36 次、12 路并发 36 次、另起 28 个忙循环进程占满 20 核时 3 路并发 15 次）。
- 修复前（对照）：measure 45 次、builtins-off 81 次都没挂，同样的三种负载都复现不了；原来的失败出在 `mq:verify` 同时链接 `build:exe` 的时候。原因靠上面的探针和实测耗时确认，不靠复现。
