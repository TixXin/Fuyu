# 任务

开工前读这一份就够：规则、分组和命令都在这里。具体有哪些任务用命令看，不用逐个打开文件。

## 先跑这几条

- `pnpm tasks next`：现在能认领的任务，按优先级排好；也列出认领已失效、可以接手的。
- `pnpm tasks show <编号>`：一项的全文，连同父任务、子任务、依赖、依赖它的任务和正文里链接的文件。
- `pnpm tasks`：完整看板。最上面是「需要你」（只有用户本人能做的，和等用户确认的），然后按分组列出没结束的任务，子任务缩进在父任务下面，标出负责人、失效的认领、在等哪个依赖、issue 和有没有交接。`--all` 连归档一起列，`--json` 给岛上的任务看板插件读。

## 目录

- `docs/tasks/<分组>/<编号>.md`：没结束的任务（待做 / 进行中 / 待用户确认），例如 `docs/tasks/B/B6.md`。
- `docs/tasks/0-archive/<分组>/<编号>.md`：已完成和不做的。文件夹名以 0 开头，排在分组文件夹前面。`pnpm tasks done` / `pnpm tasks drop` 会自动移过去，不要手动挪。
- 分组文件夹就是编号的首字母（见下一节），`pnpm tasks add` 和 `pnpm tasks done` 会自动放进对应的文件夹；放错了 `pnpm check:tasks` 会报错。
- 不删任务文件。决定不做就 `drop` 并写原因，以后有人想做时能看到当初为什么没做。

## 分组

编号的首字母就是分组，看板按下表的顺序排，这也是优先级。要新分组就在表里加一行。

| 分组 | 名称 | 放什么 |
|---|---|---|
| A | Agent 会话定位 | 点会话跳到它的终端、编辑器或标签页 |
| B | Agent 页体验 | Agent 页、会话卡片、提醒、音效、审批和提问（B6 是「Agent 岛上交互」的总任务） |
| C | 竞品都有、我们还缺的 | 新功能模块 |
| D | 质量与发布 | 测试、性能、无障碍、发布和更新 |
| E | 插件平台 | 插件 API、插件市场和 SDK |
| F | 多会话协作 | 合入流程、任务流程这些开发工具 |
| G | macOS 适配 | 让浮屿在 Mac 上可用并正式发布（G1 是总任务，计划见 `docs/architecture/macos-port-plan.md`） |

编号：分组字母加数字（`C11`）；从某项拆出来的加小写字母（`C9b`）；分期的子任务用点（`B6.2.7`，第 2 期第 7 项），同时写 `parent`。

## 头部字段

| 字段 | 说明 |
|---|---|
| `id` | 和文件名一致 |
| `title` | 一句话说清做什么；看板只显示这一行 |
| `status` | 见下一节 |
| `owner` / `host` / `claimed` | 认领的会话名、机器名和时间，由 `task:claim` 写。结束后只留 `owner` 作记录。旧任务里的 `lane`（lane 编号，2026-11-13 前）照样能读 |
| `scope` | 要改的目录（以 `/` 结尾）和文件，逗号分隔。认领时和别人的范围比对，`pnpm tasks conflicts` 也用它 |
| `depends` | 要等哪些任务先结束，逗号分隔。没结束时看板标「等 X」，认领会被拒绝（`--force` 越过） |
| `parent` | 父任务。有子任务的任务不能认领，认领子任务；看板显示「子任务 x/y」 |
| `needs` | `user`：只有用户本人能做（要别人的日志、要换电脑实测）。看板放进「需要你」，`next` 不列，认领要 `--force` |
| `issue` | 对应的 GitHub issue 编号（只写数字） |
| `done` | 完成日期 `YYYY-MM-DD`，`pnpm tasks done` 写 |

空字段不写。别的字段 `pnpm check:tasks` 会报错。

## 状态

| 状态 | 含义 |
|---|---|
| `待做` | 没人认领。不能有 `owner` / `host` / `lane` |
| `进行中` | 有会话在做（有子任务的父任务例外，它没有负责人） |
| `待用户确认` | 做到一半，等用户回答或验收；写清楚等的是什么。看板放进「需要你」 |
| `已完成` | 在 `0-archive/`，有 `done` 日期，`## 提交` 下至少一项 |
| `不做` | 在 `0-archive/`，`## 备注` 写了原因 |

## 正文

只用下面这些二级标题，按这个顺序，用不上的省掉：

1. `## 说明`：要做什么、为什么。不要重复标题；标题已经说清楚时可以没有这一节。
2. `## 验收`：怎样算做完，一条一行。新任务尽量写。
3. `## 提交`：一项一行，写 `` `提交标题` ``（一字不差）或提交号。`pnpm tasks done` 自动写。
4. `## 备注`：过程中的发现、用户的决定、没做的部分。
5. `## 结论`：调研、对比、实测这类任务的结果，可以带日期：`## 结论（2026-11-08）`。
6. `## 交接`：`pnpm tasks note` 一次加一行，带时间和会话名。接手的会话读完后，把已经过时的几行挪进备注，交接只留最新进度和下一步。

第一个标题前不放文字。链接仓库里的文件从根目录写：`[方案](/docs/architecture/x.md)`，因为任务结束时会移到 `0-archive/`，相对链接会断。

## 流程

认领看本地和 `origin/main`，不等其他会话回消息。

1. **挑**：`pnpm tasks next`，再 `pnpm tasks show <编号>` 读全文。
2. **认领**：`pnpm task:claim <编号> --as <会话名> --scope <要改的目录/,文件>`。会话名用 ListAgents 里自己的名字，必须写。它先 `git fetch origin main`，本地或 `origin/main` 上已经有人认领就拒绝；否则写上会话名和机器名，在本地提交（只含任务文件），随下一批 PR 推上去（见 [workflow.md](/docs/architecture/workflow.md)）。会话名和机器名都对上才算「你的」，另一台机器上同名的会话不算（#153）。`--no-commit` 只改文件不提交。任务带 `issue` 时，**认领后、动手前先在 issue 下回复**：谁接手、核实的结果、打算怎么改，附任务文档链接（用户 2026-11-14 定，命令会提醒）。
3. **新任务先提 issue**（见下文「自己新建的任务」），拿到编号后再建。马上要做：`pnpm tasks add <编号> --title .. --issue <N> --claim --as <会话名> --scope ..`，新建和认领在一个提交里。只是记下来以后做：`pnpm tasks add <编号> --title .. --issue <N>`，和别的改动一起提交。
4. **做的过程中**：开发中途和 land 前跑 `pnpm tasks conflicts`，看和 main、和别人声明的范围有没有冲突。
5. **停下来**：`pnpm tasks note <编号> "<进度和下一步>"`，随下一次提交带上。不打算做完了：`pnpm tasks release <编号> --reason ".."`，放回待做并留交接。
6. **做完**：`pnpm tasks done <编号> --commit "<功能提交的标题>"`（可以写多个，也可以写已有的提交号），和功能改动放在同一个提交里。本地 `main` 上有别的会话的提交，所以 `--commit` 必须写。父任务在最后一个子任务结束后 `done`。
7. **不做**：`pnpm tasks drop <编号> --reason ".."`。
8. **失效的认领**：`pnpm tasks` / `pnpm tasks stale` 标出认领后 24 小时任务文件没有新的交接或提交的认领（做得久的任务停下时 `tasks note` 留交接，也就续上了）。接手前给原会话发一条消息说明，不必等回复，`pnpm task:claim <编号> --takeover`。

land 时会自动检查（`scripts/land-check.mjs` 调 `pnpm tasks landing`）：这次标成已完成的任务，`## 提交` 里的标题要在这次 land 或 main 上一字不差，提交号要存在，否则 land 失败；本机认领、还是「进行中」的任务会提醒先 `done` 或留交接。

## GitHub issue

`TixXin/fuyu` 的 issue 一律按这个顺序处理（用户 2026-11-09 定）：

1. **核实**：读 issue，在代码里或真机上确认（能复现就先复现）。
2. **先回复，再动手**：说明已收到、初步判断和打算怎么做；要报告人补信息就在这里问。不做的（重复、不是问题、超出范围）回复原因后 `gh issue close <N> --reason "not planned"`，到此为止。
3. **建任务**：`pnpm tasks add <编号> --title .. --issue <N> --claim --as <会话名> --scope ..`。回复里引用任务文档的链接（`https://github.com/TixXin/fuyu/blob/main/docs/tasks/<分组>/<编号>.md`）；任务建好之前写的回复，在建好后补一条带链接的。
4. **做完回复**：合入 main 后回复原因、改了什么、怎么拿到（下个版本 / 插件市场 / npm），以及验证结果；引用任务文档（这时在 `docs/tasks/0-archive/<分组>/<编号>.md`），并列出这次的提交（短提交号加标题，GitHub 会自动链接）。
5. **关闭**：回复之后 `gh issue close <N>`。合入 main 就关，不等发版：回复里写明随哪个版本发布，没修好时报告人可以重新打开。不用提交说明里的 `Closes #N`：它会在完成回复之前就把 issue 关掉。

回复用中文，署名 tixxin Agent Team，可以介绍真实的自动化流程（多个会话并行、攒批开 PR、合入前的检查），不写做不到的事；最后一行写「由 <模型名> 自动整理回复」，模型名用实际在用的（例如 Opus 5.5）。

### 自己新建的任务

会话自己发现、自己要记的任务也要有 issue（用户 2026-11-13 定），这样每项工作在 GitHub 上都看得到、能讨论。

1. **先提 issue**：`gh issue create --repo TixXin/fuyu`，标题写 `[<编号>] <任务标题>`，正文写清要做什么、为什么、怎样算做完，和任务文件的「说明」「验收」一致，并给出任务文档的链接。语言、署名和最后一行同上。
2. **再建任务**：`pnpm tasks add <编号> --title .. --issue <N>`。
3. **认领时先在 issue 下回复**（用户 2026-11-14 定）：认领任务的会话动手前回复一条，说明谁接手、核实的结果和打算怎么改，链接任务文档；提 issue 时已经写了判断的，这条回复写核实结果和具体改法。有人在 issue 里评论时照常回复。
4. **做完回复、关闭**：和上面的第 4、5 步一样。决定不做时回复原因，`gh issue close <N> --reason "not planned"`，任务 `drop`。

父任务下的子任务各提各的 issue。用户在对话里直接交代、当场做完的小改动不建任务，也就不用提 issue。

## GitHub PR

别人提的 PR（含协作者的）由仓库管理员的会话来合时，和 issue 一样先回复、后动手、合完再回复（用户 2026-11-09 定）。怎么合（不走 land）见 [workflow.md](/docs/architecture/workflow.md)「外部 PR」。

1. **核实**：读说明和改动，看 PR 上 CI 的 `check`；要看界面效果或改动风险大时，再在临时 worktree 里把它合到最新的 `origin/main` 上验证，验完删掉，这个合并不推送。
2. **先回复，再合**：说明已收到、看法（合 / 要作者改 / 不合）、检查的结果和接下来怎么做。要作者改的，写清楚改哪里，等作者推上来再从第 1 步走。不合的回复原因后 `gh pr close <N>`，到此为止。
3. **跟进建任务**：合入后还要我们自己补的（作者没做的部分、顺带发现的问题），`pnpm tasks add <编号> --title .. --issue <PR 号>`（PR 和 issue 共用编号，`issue` 字段写 PR 号即可），第 2 步的回复里引用任务文档；任务建好之前写的回复，建好后补一条带链接的。PR 本身就是做好的改动，不为它另建任务。
4. **合入**：`gh pr merge <N> --auto --merge` 开启自动合并，CI 的 `check` 通过后 GitHub 合入，落后于 `main` 时由工作流排队更新；`pnpm mq:wait <N>` 等到合入并把本地 `main` 跟上。合入时 PR 自动关闭。
5. **合完回复**：写合并提交号、怎么拿到（下个版本 / 插件市场 / npm）和验证结果；有跟进任务的，任务做完后再回复一条，引用任务文档（这时在 `0-archive/`）并列出跟进的提交（短提交号加标题）。

回复的语言、署名和最后一行同上一节。

## 校验

`pnpm check:tasks`（在 `pnpm check` 里）检查：编号格式和分组、文件名、所在的分组文件夹、未知字段、状态和所在目录是否对应、待做没有负责人、依赖和父任务存在、已完成有日期和提交、不做有原因、正文标题和顺序、没有重复标题、没有相对链接。
