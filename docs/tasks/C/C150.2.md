## 说明

2026-11-13 实测 3072×1728：把约 2100 万字节的画面经 IPC 传进页面再 `putImageData` 要 260–380 ms（debug）。窗口已经先显示，但这段时间里取色、放大镜、带标注的完成都不能用。试几种做法再定：传压缩后的图（PNG / QOI / WebP 无损）交给 `createImageBitmap` 解码、按显示器分块传、或用自定义协议让页面直接取。先量再改，数字写进备注。

## 验收

- release 版 4K 单屏从按下快捷键到放大镜可用的时间有前后对比数字，目标 150 ms 以内
- 多显示器、混合缩放下画面位置不变
- `pnpm check`、`pnpm build`、`cargo test`、`pnpm build:exe`

## 备注

### 2026-11-20 Mac 上先量（shot-batch1）

探测程序 `src-tauri/examples/screenshot_frame_probe.rs`：一个独立的 Tauri 窗口，用自定义协议把一帧整屏 RGBA 交给页面（和 `screenshot_frame` 走的 `ipc://` 原样返回是同一条路），每种做法先热身一轮再跑 6 轮取中位数，结果打印到终端后自己退出。命令：

```bash
pnpm heavy -- cargo build --release --manifest-path src-tauri/Cargo.toml --example screenshot_frame_probe
src-tauri/target/agents/release/examples/screenshot_frame_probe <一张真实截图.png>
```

MacBook Air 外接 4K 屏，release，3840×2160（3300 万字节），WKWebView，单位 ms：

| 做法 | 取到字节 | 画上 canvas | 到下一帧画面 | 其他 |
|---|---|---|---|---|
| 原样传 + `putImageData`（现在的做法） | 17 | 11 | 43 | Rust 复制 2.3 |
| 原样传 + `createImageBitmap` + `drawImage` | 17 | 22 | 49 | |
| 分 4 块并行取 + `putImageData` | 15 | 14 | 43 | |
| PNG（快速压缩，400 万字节）+ `createImageBitmap` | 6 | 149 | 173 | Rust 编码 43，取回像素给取色再要 6 |

结论：Mac 上原样传已经是最快的，压缩反而慢 4 倍，传输和绘制合起来不到 50 ms，不用改。任务说明里的 260–380 ms 是 debug 版（多半还是 Windows），release 不是这个量级。

同一台机器上，`macos/screen_capture.rs` 的 `capture` 截主屏 3840×2160（debug，含每次重新取 `SCShareableContent` 和 BGRA→RGBA 换算）：第一次 780 ms，之后 170–225 ms。所以 Mac 上「按下快捷键到放大镜可用」大头在截屏本身，不在送进页面；要往 150 ms 以内压，下一步看截屏：release 下换算的耗时、能不能复用 `SCShareableContent`、冷启动那一下能不能在启动时预热。

还没做：Windows（WebView2 的自定义协议大响应一向慢，最可能就是那 260–380 ms 的来源）上跑同一个探测程序；两个平台在真岛上量「快捷键到放大镜可用」的端到端数字。Windows 上如果原样传明显慢，候选是 WebView2 的 `PostSharedBufferToScript`（共享内存，零复制）。
