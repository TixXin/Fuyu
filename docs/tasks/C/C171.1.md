## 说明

现状和原因见 [调研](/docs/research/peripheral-battery.md)「2026-11-22」和 [C171](/docs/tasks/C/C171.md) 的共同约定。要改的地方：

1. **BLE 不再按外观值预筛**（`win32/ble_battery.rs`）：`connected_devices` 去掉 `wanted(appearance)` 这道门，所有已连接的 BLE 设备都读电池服务（BlueGauge 的做法）；返回外观值、地址、名字、电量和 ContainerId（用 `DeviceInformation` 的 `System.Devices.ContainerId` 或设备节点取）。读不到电量的设备不返回。注意单台设备读电量可能卡几秒，给整轮读数设上限或逐台超时，别拖住每秒一次的音频输出轮询（`device_events/mod.rs` 的 `watch`）；必要时把外设读数挪到单独线程。
2. **定类型**：外观值是键盘 / 鼠标就用它；否则看同一 ContainerId 下 `HID` 枚举器里设备的类别 GUID，键盘类 `{4D36E96B-E325-11CE-BFC1-08002BE10318}`、鼠标类 `{4D36E96F-E325-11CE-BFC1-08002BE10318}`；都不是（手机、手表、音频设备）就不算外设。
3. **设备节点电量**（`win32/devnode.rs`）：枚举器加上 `BTHLE`；`bluetooth_batteries()` 同时返回节点的蓝牙地址（`DEVPKEY_Bluetooth_DeviceAddress` = `{2BD67D8B-8BEB-48D5-87E0-6CDA3428040A},1`，字符串，BlueGauge 的做法；拿不到时从实例 ID 里的 `DEV_xxxxxxxxxxxx` 或 `_xxxxxxxxxxxx` 截）和名字（`DEVPKEY_Device_FriendlyName`）。
4. **不再要求音频枚举器是 `BTH…`**（`device_events/mod.rs`）：设备节点电量按 `BATTERY_POLL` 固定读，`read_now` 也一样，`has_bluetooth` 只留给提醒逻辑（如果还需要）。
5. **键鼠的设备节点电量也进列表**（`device_events/readers.rs`、`batteries.rs`）：ContainerId 属于键盘 / 鼠标类的节点电量作为外设加入，和第 1 步的 BLE 结果按地址去重，设备节点的数字优先。
6. **`read_now` 放到新线程**：`get_peripheral_batteries` 在设备提示关闭时走 `spawn_blocking` 当场读，tokio 的线程如果已经是 STA，`CoInitializeEx(MTA)` 会失败，整个返回空。改成在新的 `std::thread` 里读。
7. **探测测试**：`readers.rs` 加 `#[ignore]` 的 `probe_this_computer`，分别打印音频输出、设备节点电量（含地址、名字、ContainerId）、BLE 设备（含外观值、电量、ContainerId）、HID 子设备类别和最终列表，和 `readers_macos.rs` 里那个对应。

开发机是 Mac：用 `pnpm heavy -- cargo check --target x86_64-pc-windows-msvc --manifest-path src-tauri/Cargo.toml` 交叉检查（构建脚本过不了就如实写进交接，靠推 PR 时 CI 的 Windows 检查）；纯函数（地址解析、类型判定、合并去重）的单元测试不加 `cfg(windows)`，Mac 上也能跑。

## 验收

- 外观值不标准的 BLE 键鼠也能列出；手机、手表不会被当成外设
- 系统设置里显示电量的蓝牙耳机在组件里也有，和音频驱动是不是蓝牙枚举器无关
- 同一台设备只出现一次
- 一台设备读电量卡住时，耳机插拔提醒不变慢
- 关掉设备提示后组件照样有读数
- 提交正文写 `Manual check:`：Windows 上连 BLE 鼠标、键盘和蓝牙耳机看组件；跑 `cargo test probe_this_computer -- --ignored --nocapture` 贴输出
